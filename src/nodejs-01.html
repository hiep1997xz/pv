Event loop phía Node · các phase
?setImmediate và setTimeout(fn, 0) khác nhau chỗ nào?
?process.nextTick chạy trước hay sau Promise.then?
💡 Trả lời
  • Mỗi vòng lặp đi qua các phase theo thứ tự cố định: timers → pending callbacks → idle/prepare → poll → check → close callbacks, rồi quay lại từ đầu.
  • setTimeout chạy ở phase timers, setImmediate ở phase check. Đang trong một I/O callback (tức đang ở phase poll) thì setImmediate luôn chạy trước.
  • Ở top level thứ tự cặp đó không bảo đảm: còn tuỳ lúc event loop tới phase timers thì 1ms đã trôi qua chưa. Script 2 dòng chạy 100 lần sẽ ra cả hai thứ tự.
  • process.nextTick có queue riêng và được vét trước microtask của Promise. Cả hai queue đều vét sau mỗi callback, không phải chỉ vét giữa các phase.
  • Node chỉ có một luồng chạy JS. Một vòng for nặng hay JSON.parse file 50MB là chặn cả server — mọi request khác nằm chờ, kể cả health check.
const fs = require('node:fs');      // .cjs — output thật ở dưới
setTimeout(() => console.log('timeout'), 0);     // phase timers
setImmediate(() => console.log('immediate'));    // phase check
// ❌ ở top level thứ tự cặp trên KHÔNG bảo đảm, đừng dựa vào nó

fs.readFile(__filename, () => {                  // callback ở phase poll
  setTimeout(() => console.log('t2'), 0);
  setImmediate(() => console.log('i2'));
  // ✅ trong I/O callback: i2 LUÔN chạy trước t2
});

process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('promise'));
console.log('sync');
// ✅ ba dòng trên in ra:  sync  →  nextTick  →  promise
⚠ Bẫy phỏng vấn: Nhiều người tưởng “Node bất đồng bộ nên không bao giờ bị chặn”. Sai: chỉ I/O mới bất đồng bộ, code JS của bạn vẫn chạy một luồng. Một vòng lặp nặng làm p99 của mọi endpoint khác tăng theo.
💬 Nói thêm để ghi điểm: Chi tiết ghi điểm: ở top level của file ESM, nextTick lại chạy sau Promise.then, vì việc đánh giá module ESM vốn đã nằm trong một promise job. Trong CommonJS và trong mọi callback thì nextTick vẫn trước.
