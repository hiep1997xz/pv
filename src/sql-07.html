SQL MIDDLE 07 / 10
Lock · Deadlock · SELECT FOR UPDATE
?Deadlock xảy ra khi nào và phòng bằng cách nào?
?SELECT ... FOR UPDATE dùng để làm gì?
💡 Trả lời
  • UPDATE/DELETE tự khoá từng dòng nó chạm tới, giữ tới lúc COMMIT hoặc ROLLBACK. Nhờ MVCC, ở PostgreSQL đọc không chặn ghi, ghi không chặn đọc.
  • SELECT ... FOR UPDATE khoá trước những dòng sắp sửa, buộc transaction khác phải chờ. Đây là pessimistic lock, dùng khi đọc-rồi-ghi phải nguyên tử: trừ kho, trừ số dư.
  • FOR UPDATE NOWAIT báo lỗi ngay thay vì chờ. FOR UPDATE SKIP LOCKED bỏ qua dòng đang bị khoá — đây là mẫu chuẩn để nhiều worker cùng lấy job từ một bảng queue.
  • Deadlock sinh ra khi hai transaction khoá ngược thứ tự nhau: A giữ dòng 1 chờ dòng 2, B giữ dòng 2 chờ dòng 1. PostgreSQL phát hiện sau deadlock_timeout (1s) rồi huỷ một bên.
  • Phòng deadlock: luôn khoá theo một thứ tự cố định (ví dụ id tăng dần), giữ transaction thật ngắn, và đặt lock_timeout để không treo vô hạn.
-- ❌ A: UPDATE ... id = 1   rồi   UPDATE ... id = 2
-- ❌ B: UPDATE ... id = 2   rồi   UPDATE ... id = 1  (ngược thứ tự)
-- ERROR: deadlock detected  (PostgreSQL huỷ hẳn một bên)

-- ✅ luôn khoá theo một thứ tự cố định: id nhỏ trước
BEGIN;  -- transaction càng ngắn thì càng khó đụng deadlock
SELECT bal FROM acc WHERE id = 1 FOR UPDATE;
SELECT bal FROM acc WHERE id = 2 FOR UPDATE;
UPDATE acc SET bal = bal - 10 WHERE id = 1;
UPDATE acc SET bal = bal + 10 WHERE id = 2;
COMMIT;

-- ✅ nhiều worker lấy job mà không giẫm chân nhau
SELECT * FROM jobs WHERE status = 'queued'
ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED;
⚠ Bẫy phỏng vấn: Deadlock không chữa được bằng cách tăng timeout — nó là vòng chờ khép kín, chờ bao lâu cũng không thoát. PostgreSQL huỷ một bên nên app buộc phải bắt lỗi và retry. Nguyên nhân gần như luôn là hai đoạn code khoá theo thứ tự khác nhau.
