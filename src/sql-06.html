💡 Trả lời
  • ACID: Atomicity (ăn cả hoặc ngã về không), Consistency (không phá ràng buộc), Isolation (transaction không giẫm chân nhau), Durability (commit xong là còn, kể cả mất điện).
  • Ba hiện tượng theo chuẩn: dirty read đọc dữ liệu chưa commit · non-repeatable read đọc lại cùng một dòng ra giá trị khác · phantom read chạy lại cùng câu lọc thì có thêm dòng.
  • Bốn mức tăng dần: READ UNCOMMITTED → READ COMMITTED → REPEATABLE READ → SERIALIZABLE. Càng cao càng an toàn, đổi lại càng hay phải chờ hoặc bị huỷ transaction.
  • PostgreSQL mặc định READ COMMITTED; MySQL InnoDB mặc định REPEATABLE READ. PostgreSQL không có READ UNCOMMITTED thật — khai báo mức đó thì vẫn chạy như READ COMMITTED.
  • REPEATABLE READ của PostgreSQL dựa trên snapshot nên chặn luôn cả phantom read, chặt hơn chuẩn. Đổi lại, ghi đè dòng người khác vừa sửa sẽ nhận lỗi could not serialize access.
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT bal FROM acc WHERE id = 1;    -- đọc ra 100
-- lúc này transaction khác UPDATE rồi COMMIT, bal chỉ còn 80
UPDATE acc SET bal = bal - 10 WHERE id = 1;
-- ❌ ERROR: could not serialize access due to concurrent update
ROLLBACK;                            -- app phải tự retry lại

-- ✅ READ COMMITTED (mặc định): mỗi câu lệnh thấy bản mới nhất
BEGIN;
UPDATE acc SET bal = bal - 10 WHERE id = 1;   -- tính trên bal mới
COMMIT;
⚠ Bẫy phỏng vấn: Lost update: đọc bal về biến trong app, trừ trong code rồi UPDATE ... SET bal = 90. Hai request chạy song song thì bản ghi sau đè bản trước, tiền bốc hơi. Sửa bằng SET bal = bal - 10 ngay trong SQL, hoặc khoá dòng bằng FOR UPDATE.
💬 Nói thêm để ghi điểm: Isolation cao không thay được khoá. SERIALIZABLE ở PostgreSQL có thể huỷ transaction bất kỳ lúc nào với mã lỗi 40001, nên chọn mức này thì app bắt buộc phải có vòng retry.
