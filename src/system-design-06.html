Rate limit · Idempotency · Retry

?Làm sao để API thanh toán không trừ tiền hai lần?
💡 Trả lời
  • Token bucket: bucket chứa N token, đổ lại r token mỗi giây, mỗi request tiêu 1 token. Cho phép burst tới N mà vẫn giữ tốc độ trung bình r. Nhẹ, mỗi key chỉ lưu 2 con số.
  • Fixed window dễ làm nhưng thủng ở mép: dồn request vào cuối phút này và đầu phút sau, trong ~1 giây có thể lọt gấp đôi hạn mức. Sliding window chính xác hơn, tốn bộ nhớ hơn.
  • Đặt ở đâu: CDN hoặc WAF chặn tấn công lớp mạng, API gateway chặn theo API key, service chặn theo nghiệp vụ. Vượt hạn mức thì trả 429 kèm header Retry-After.
  • Idempotency key: client sinh UUID gửi kèm request tạo đơn hay thanh toán. Server lưu key cùng kết quả; key trùng thì trả lại kết quả cũ chứ không thực hiện lần hai.
  • Retry phải có exponential backoff + jitter và giới hạn số lần. Chỉ retry lỗi tạm thời (timeout, 5xx, 429); lỗi 4xx thì retry bao nhiêu lần cũng vẫn sai, chỉ tốn thêm tải.
// ✅ backoff mũ + jitter: các client không retry cùng một nhịp
async function goiLai(fn, max = 3) {
  for (let i = 0; i < max; i++) {
    try { return await fn(); }
    catch (e) {
      if (e.status < 500 && e.status !== 429) throw e;  // 4xx: bỏ luôn
      const base = 2 ** i * 100;                        // 100, 200, 400
      await nghi(base + Math.random() * base);          // jitter
    }
  }
  throw new Error('hết lượt retry, mở circuit breaker');
}
// ❌ retry đều tay, không jitter: dịch vụ vừa hồi phục đã bị
// cả ngàn client đập lại cùng lúc → sập tiếp (retry storm)
⚠ Bẫy phỏng vấn: Retry mù là nguyên nhân kinh điển gây sập dây chuyền: service chậm → client retry → tải tự nhân lên nhiều lần → service chết hẳn. Thiếu jitter thì mọi client cùng thức dậy tại một mốc thời gian.
💬 Nói thêm để ghi điểm: Nhắc circuit breaker: tỉ lệ lỗi vượt ngưỡng thì mở mạch, fail nhanh một lúc rồi chuyển sang nửa mở để thăm dò. Ghép với Retry-After ở 429 để client biết chờ bao lâu thay vì đoán.
