Index · Đọc EXPLAIN ANALYZE
?Index (a, b) có phục vụ được WHERE b = ? không?
?Vì sao bọc hàm lên cột lại làm mất index?
💡 Trả lời
  • B-tree là loại index mặc định, phục vụ =, khoảng < > BETWEEN và cả ORDER BY. Cột chọn lọc kém (chỉ vài giá trị khác nhau) thì đánh index gần như vô ích.
  • Quy tắc tiền tố trái: index (a, b, c) phục vụ WHERE a, WHERE a AND b, WHERE a AND b AND c — nhưng không phục vụ WHERE b đứng một mình.
  • Bọc hàm lên cột là index chết: WHERE lower(email) = ... rơi về Seq Scan. Cứu bằng expression index: CREATE INDEX ... đánh thẳng lên (lower(email)).
  • Covering index: index chứa đủ mọi cột câu lệnh cần → PostgreSQL đọc thẳng từ index, kế hoạch hiện Index Only Scan, khỏi chạm bảng. Gắn thêm cột phụ bằng INCLUDE (...).
  • Đọc EXPLAIN ANALYZE: Seq Scan là quét cả bảng, Index Scan là dò index. So rows= (ước lượng) với actual rows= (thật) — lệch nhiều là thống kê đã cũ.
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'a@ex.com';
-- ✅ Index Scan using idx_users_email   (actual rows=1)

-- ❌ bọc hàm lên cột → Seq Scan, quét trọn bảng
SELECT 1 FROM users WHERE lower(email) = 'a@ex.com';

-- ✅ expression index cứu đúng câu ở trên
CREATE INDEX idx_users_email_lower ON users (lower(email));

-- composite index: thứ tự cột quyết định tất cả
CREATE INDEX idx_u_city_name ON users (city, name);
-- ✅ WHERE city = 'HN'                → dùng được
-- ✅ WHERE city = 'HN' AND name = 'x' → dùng được
-- ❌ WHERE name = 'x'                 → bỏ qua index, Seq Scan
⚠ Bẫy phỏng vấn: Đánh index rồi vẫn chậm thì soi ba thứ: điều kiện có bọc hàm lên cột không, cột lọc có phải tiền tố trái của composite index không, và kiểu dữ liệu hai vế có khớp không — ép kiểu ngầm cũng đủ làm planner bỏ index.
💬 Nói thêm để ghi điểm: Index không miễn phí: mỗi INSERT/UPDATE phải cập nhật mọi index của bảng. Trước khi thêm cái mới, dọn cái thừa — soi pg_stat_user_indexes, cột idx_scan bằng 0 là chưa ai dùng.
