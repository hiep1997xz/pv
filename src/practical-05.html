💡 Trả lời
  • Polling hợp khi dữ liệu đổi chậm và trễ vài giây chấp nhận được. Đơn giản nhất, không phải nuôi kết nối — đừng vội chê.
  • SSE một chiều server → client, chạy trên HTTP thường: tự reconnect sẵn, có Last-Event-ID, qua proxy dễ. Hợp notification, feed, tiến độ job.
  • WebSocket hai chiều, độ trễ thấp, hợp chat và collab. Đổi lại phải tự làm reconnect, heartbeat, auth và scale khó hơn hẳn.
  • Reconnect phải có exponential backoff + jitter, không thì server vừa sống lại là cả vạn client đập vào cùng lúc. Heartbeat ping/pong để phát hiện kết nối đã chết.
  • Đồng bộ lại sau mất kết nối: mỗi message có seq/id, reconnect thì gửi id cuối đã nhận để server bù phần thiếu. Client phải dedupe vì giao hàng là at-least-once.
let retry = 0, lastId = '';
function connect() {
  const ws = new WebSocket(`${URL}?since=${lastId}`);  // bù phần thiếu
  ws.onopen = () => { retry = 0; };
  ws.onmessage = (e) => {
    const m = JSON.parse(e.data);
    if (seen.has(m.id)) return;      // ✅ dedupe: at-least-once
    seen.add(m.id); lastId = m.id; push(m);
  };
  // ❌ reconnect ngay lập tức → cả vạn client đập vào server vừa sống
  ws.onclose = () => {
    const ms = Math.min(30_000, 2 ** retry++ * 1000);
    setTimeout(connect, ms * (0.5 + Math.random()));  // ✅ có jitter
  };
}
⚠ Bẫy phỏng vấn: Scale WebSocket qua nhiều server: không sticky session thì reconnect rơi sang node khác, mà danh sách subscribe nằm trong RAM node cũ → client kết nối thành công nhưng im lặng mãi mãi. Cần Redis pub/sub để fan-out giữa các node.
💬 Nói thêm để ghi điểm: SSE hay bị proxy buffer lại làm message kẹt — tắt proxy_buffering của Nginx hoặc gửi header X-Accel-Buffering: no. Load balancer cũng thường cắt kết nối idle sau 60s, đó là lý do thật sự cần heartbeat.
