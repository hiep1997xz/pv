Migration & Seed khi deploy
?Migration chạy ở bước nào trong quy trình deploy?
?Sửa migration đã chạy trên production được không?
💡 Trả lời
  • Công cụ: prisma migrate deploy, drizzle-kit migrate, knex migrate:latest, node-pg-migrate. Cái nào cũng giữ một bảng lịch sử để không chạy lại migration cũ.
  • Chạy migration ở một job riêng trong pipeline, xong mới cho pod mới nhận traffic. Không gọi trong app.listen(): 4 instance khởi động cùng lúc là 4 tiến trình cùng ALTER TABLE.
  • Không bao giờ sửa migration đã chạy trên production. Lịch sử và checksum lệch thì công cụ hoặc báo lỗi, hoặc tệ hơn là bỏ qua âm thầm. Sai thì viết một migration mới đè lên.
  • Migration phải tương thích ngược với code đang chạy, vì lúc rollout code cũ và mới sống chung vài phút. Đổi tên cột = thêm cột mới → ghi cả hai → chuyển đọc → xoá cột cũ.
  • Seed chia hai loại: dữ liệu tham chiếu (role, config) chạy mọi môi trường; dữ liệu giả chỉ ở dev/test. Test phải chạy trên Postgres thật — mock DB thì không kiểm tra được gì.
// ❌ src/main.ts — 4 pod khởi động cùng lúc = 4 lần ALTER TABLE
await migrateOnBoot();
app.listen(3000);

// ✅ một job riêng trong pipeline, xong mới rollout pod mới
//   deploy.sh:
//     npx prisma migrate deploy    # 1 job duy nhất, chờ chạy xong
//     kubectl rollout restart deploy/api

// ✅ đổi tên cột an toàn: 3 lần deploy, không lần nào gãy code cũ
// 1) ALTER TABLE users ADD COLUMN full_name text;  (code cũ vẫn chạy)
// 2) app ghi cả name lẫn full_name + backfill dữ liệu cũ
// 3) app đọc full_name → deploy → ALTER TABLE users DROP COLUMN name;
⚠ Bẫy phỏng vấn: Chạy migration lúc app khởi động với nhiều instance: hai tiến trình cùng vào một migration, một cái chết vì “relation already exists” rồi crash-loop, hoặc hai cái khoá bảng lẫn nhau. Sự cố 2 giờ sáng thường bắt đầu đúng từ đây.
💬 Nói thêm để ghi điểm: Từ Postgres 11, ADD COLUMN có DEFAULT không còn viết lại cả bảng nữa. Nhưng CREATE INDEX vẫn khoá ghi — dùng CREATE INDEX CONCURRENTLY, và nhớ là nó không chạy được bên trong transaction.
