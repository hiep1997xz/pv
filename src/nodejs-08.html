?Memory leak trong Node thường đến từ đâu?
💡 Trả lời
  • Đo trước, tối ưu sau. Bốn số cần nhìn: event loop lag, p95/p99 theo từng endpoint, RSS và heap used, số kết nối đang xếp hàng chờ trong pool DB.
  • monitorEventLoopDelay cho biết event loop bị giữ bao lâu. p99 lag vài trăm ms nghĩa là có việc đồng bộ nặng — thường là JSON.parse, regex tham lam, hoặc vòng lặp trên mảng to.
  • Nguồn leak hay gặp: cache toàn cục chỉ thêm không xoá, emitter.on đăng ký lại mỗi request mà quên off, closure giữ tham chiếu tới object lớn, timer không clearInterval.
  • Bắt leak bằng heap snapshot: chụp hai lần cách nhau rồi so phần tăng thêm trong Chrome DevTools. v8.writeHeapSnapshot() chụp được ngay trên production, không cần dựng lại.
  • Structured logging (JSON) kèm correlation id đi theo request qua mọi service. Dùng AsyncLocalStorage để khỏi phải nhét id vào chữ ký của mọi hàm.
import { monitorEventLoopDelay } from 'node:perf_hooks';
import { AsyncLocalStorage } from 'node:async_hooks';
const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
setInterval(() => {
  console.log({ lagP99ms: +(h.percentile(99) / 1e6).toFixed(1) });
  h.reset();
}, 10_000).unref();

const als = new AsyncLocalStorage();   // correlation id đi theo request
app.use((req, res, next) =>
  als.run({ reqId: req.get('x-request-id') ?? randomUUID() }, next));

// ✅ mọi lời gọi ra ngoài đều phải có hạn, nếu không sẽ treo vô hạn
await fetch(url, { signal: AbortSignal.timeout(3000) });
⚠ Bẫy phỏng vấn: Đừng nói “RSS tăng là leak”. V8 chỉ gom rác khi thấy cần, RSS lên rồi phẳng ra là bình thường. Leak thật là heap used sau full GC vẫn tăng đều qua nhiều giờ — ép GC rồi mới đo thì kết luận mới đứng được.
💬 Nói thêm để ghi điểm: AbortSignal.timeout là cách ngắn nhất để mọi lời gọi ra ngoài đều có hạn. Thiếu timeout thì một dependency chậm sẽ giữ hết kết nối trong pool và kéo sập cả những endpoint chẳng liên quan gì tới nó.
