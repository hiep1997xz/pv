System Design MIDDLE 02 / 08
Scale · Load balancer · Stateless
?Scale ngang khác scale dọc ở điểm nào?
?Vì sao app server bắt buộc phải stateless?
💡 Trả lời
  • Vertical = nâng cấu hình một máy: nhanh, không đụng code, nhưng có trần phần cứng và vẫn là một điểm chết duy nhất. Horizontal = thêm máy: không trần, đổi lại phải lo state.
  • Stateless nghĩa là app không giữ dữ liệu phiên trong RAM tiến trình. Request rơi vào máy nào cũng xử lý được → thêm máy, rút máy, deploy hay máy chết đều không mất phiên.
  • Session đặt ở store dùng chung (Redis) hoặc gói vào JWT phía client. JWT khỏi tra cứu nhưng khó thu hồi trước hạn — phải có TTL ngắn kèm refresh token, hoặc danh sách chặn.
  • Sticky session ghim user vào một máy: dễ làm nhưng tải lệch, máy chết là mất phiên, auto-scale không rút được máy cũ. Coi nó là giải pháp tạm, không phải kiến trúc.
  • Health check: LB gọi /health định kỳ, fail vài lần liên tiếp thì rút máy khỏi pool. Thuật toán hay dùng: round robin, least connections, consistent hashing.
              ┌────────────┐
 client ─────▸│     LB     │  // health check, fail 3 lần → rút
              └─────┬──────┘
        ┌───────────┼───────────┐
        ▼           ▼           ▼
    ┌───────┐   ┌───────┐   ┌───────┐  // app stateless: không giữ
    │ app 1 │   │ app 2 │   │ app 3 │  // session trong RAM tiến trình
    └───┬───┘   └───┬───┘   └───┬───┘
        └───────────┼───────────┘
                    ▼
          ┌──────────────────┐
          │  Redis  session  │  // ✅ state dùng chung, máy nào
          └──────────────────┘  //    cũng đọc được phiên của user
⚠ Bẫy phỏng vấn: Đừng trả lời “cứ thêm server là scale được”. Câu vặn ngay sau đó: session đang nằm ở đâu? Nếu session nằm trong RAM từng app thì thêm máy = user bị đăng xuất ngẫu nhiên khi LB đổi đích.
💬 Nói thêm để ghi điểm: Tách rõ phần stateless (app) và phần stateful (DB, Redis, file). Scale phần stateless là chuyện dễ; cái khó luôn nằm ở phần stateful — chủ động nói ra chỗ đó là ghi điểm.
