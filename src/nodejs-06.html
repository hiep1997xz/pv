Stream · Backpressure · File lớn
?Backpressure trong stream là gì và ai lo chuyện đó?
?Vì sao nên dùng pipeline thay cho chuỗi .pipe()?
💡 Trả lời
  • Bốn loại: Readable (nguồn), Writable (đích), Duplex (hai chiều, ví dụ socket), Transform (duplex có biến đổi, ví dụ gzip hoặc parse CSV).
  • Backpressure: khi đích ghi chậm hơn nguồn đọc, write() trả về false, nguồn phải ngừng đọc và chờ sự kiện drain. Bỏ qua tín hiệu này là dữ liệu dồn hết trong RAM.
  • fs.readFile nạp toàn bộ file vào một Buffer. File 2GB thì vừa đụng trần heap, vừa chặn event loop lúc cấp phát, và chỉ vài request song song là hết RAM máy.
  • pipeline() lo lỗi và dọn dẹp: một khâu hỏng thì mọi stream trong chuỗi bị destroy. Chuỗi .pipe() thì nguồn vẫn mở khi đích lỗi, rò dần file descriptor.
  • Bản trong stream/promises cho phép await pipeline(...), ghép với try/catch như code bình thường. Truyền thêm signal để huỷ khi client ngắt kết nối.
import { createReadStream, createWriteStream } from 'node:fs';
import { createGzip } from 'node:zlib';
import { pipeline } from 'node:stream/promises';

// ❌ readFile (fs/promises) nạp cả 2GB vào Buffer → đụng trần heap
const buf = await readFile('big.csv');
res.end(buf);

// ✅ chảy theo từng chunk, RAM gần như không đổi dù file to cỡ nào
try {
  await pipeline(createReadStream('big.csv'), createGzip(),
                 createWriteStream('big.csv.gz'));
} catch (err) {
  // pipeline đã destroy sạch mọi stream trong chuỗi trước khi ném ra
}
⚠ Bẫy phỏng vấn: Hỏi vặn: “.pipe() có lo backpressure không?” → Có, backpressure thì .pipe() lo được. Thứ nó không lo là lỗi: đích hỏng thì nguồn không được đóng, file descriptor rò dần tới lúc cạn.
💬 Nói thêm để ghi điểm: Trong HTTP, req là Readable còn res là Writable — upload lớn thì cho pipeline nối thẳng req sang createWriteStream, khỏi giữ file trong RAM. Tăng highWaterMark khi throughput quan trọng hơn độ trễ.
