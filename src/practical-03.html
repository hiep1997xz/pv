Auth · Access token & Refresh token
?Lưu access token ở localStorage có an toàn không?
?Nhiều request cùng dính 401 thì refresh ra sao?
💡 Trả lời
  • Cookie httpOnly + Secure + SameSite: JS không đọc được nên XSS không lấy được token ra ngoài. localStorage thì mọi script trên trang, kể cả thư viện bên thứ ba, đều đọc được.
  • Access token sống ngắn (5–15 phút), refresh token sống dài và nên rotate mỗi lần dùng. Server phát hiện refresh token cũ bị dùng lại thì thu hồi cả phiên.
  • Refresh ngầm: interceptor bắt 401 → gọi /auth/refresh → phát lại request cũ. Bắt buộc có cờ _retry để không lặp vô hạn khi refresh cũng 401.
  • Gộp refresh bằng single-flight: giữ một promise dùng chung, mọi request 401 cùng chờ promise đó rồi mới chạy lại.
  • Đăng xuất nhiều tab: phát tín hiệu qua BroadcastChannel hoặc sự kiện storage. Dùng cookie thì phải chống CSRF: SameSite=Lax/Strict, thêm CSRF token cho request cross-site.
let refreshing: Promise<unknown> | null = null;

api.interceptors.response.use(undefined, async (err) => {
  const req = err.config;
  if (err.response?.status !== 401 || req._retry) throw err;
  req._retry = true;                      // ✅ chỉ thử lại đúng 1 lần
  // ✅ gộp N request 401 vào 1 lần refresh (single-flight)
  refreshing ??= api
    .post('/auth/refresh')
    .finally(() => { refreshing = null; });

  await refreshing;
  return api(req);                        // phát lại request cũ
});
⚠ Bẫy phỏng vấn: Không gộp refresh là bug khó chịu nhất: 8 request song song cùng 401 → bắn 8 lần refresh. Với refresh token rotation, lần đầu đổi token xong thì 7 lần sau cầm token đã cũ → server coi là tái sử dụng và đá user ra ngẫu nhiên.
💬 Nói thêm để ghi điểm: Đừng nói httpOnly cookie là miễn nhiễm XSS. Kẻ tấn công tuy không đọc được token nhưng vẫn gọi API thay mặt user ngay trên tab đó. httpOnly chỉ chặn việc mang token đi nơi khác.
