Migration an toàn trên production
?Đổi tên một cột mà không downtime thì làm sao?
?Migration nào không rollback được?
💡 Trả lời
  • Expand-contract: mở rộng trước (thêm cột mới, tương thích ngược), ghi cả hai, backfill, chuyển đọc sang cột mới, rồi mới contract (xoá cột cũ) ở một release sau.
  • Nguyên tắc gốc: mỗi bước phải chạy được với cả code cũ lẫn code mới. Lúc rolling deploy, hai bản chạy song song trong nhiều phút — đổi tên cột một phát là bản cũ chết ngay.
  • Thêm cột NOT NULL không DEFAULT lên bảng đã có dữ liệu là fail ngay. Cách an toàn chung: thêm cột nullable → backfill theo lô → mới thêm ràng buộc.
  • Tạo index trên bảng đang chạy phải dùng CREATE INDEX CONCURRENTLY: không khoá ghi, chạy lâu hơn, không chạy trong transaction, fail thì để lại index INVALID phải drop tay.
  • Không rollback được: DROP COLUMN, DROP TABLE, và mọi phép đổi kiểu làm mất thông tin. Tách chúng thành release riêng, chạy sau khi bản mới đã sống ổn vài ngày.

// ✅ tạo index trên bảng đang chạy, không chặn ghi
CREATE INDEX CONCURRENTLY idx_users_email ON users (email);
// ❌ CONCURRENTLY không chạy được bên trong một transaction
⚠ Bẫy phỏng vấn: Câu vặn hay gặp: "thêm cột NOT NULL DEFAULT lên bảng 50 triệu dòng thì sao?" Postgres từ 11 chỉ ghi metadata nên nhanh; bản cũ hơn viết lại toàn bộ bảng và giữ ACCESS EXCLUSIVE — mọi đọc và ghi treo hàng chục phút.
💬 Nói thêm để ghi điểm: Đặt lock_timeout ngắn cho session chạy migration: không lấy được khoá thì fail nhanh rồi thử lại. Hàng đợi khoá ở Postgres chặn dây chuyền — một lệnh ALTER đang chờ sẽ giữ luôn mọi query xếp sau nó.
