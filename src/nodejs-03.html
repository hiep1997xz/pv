Async · Lỗi · Error middleware
?Vì sao try/catch không bắt được lỗi trong callback?
?Gặp uncaughtException thì nên xử lý thế nào?
💡 Trả lời
  • try/catch chỉ bao được phần chạy đồng bộ bên trong nó. Callback của setTimeout hay của stream chạy ở tick sau, lúc đó stack cũ đã tan — lỗi bay thẳng ra ngoài.
  • Với async/await thì try/catch lại bắt được, nhưng bắt buộc phải có await. Quên await là promise reject lọt ra thành unhandledRejection.
  • Express 4 không tự bắt promise reject trong handler: phải .catch(next) hoặc bọc bằng một hàm wrapper. Express 5 thì bắt được, nên hỏi rõ phiên bản trước khi trả lời.
  • Error middleware của Express phải khai báo đủ 4 tham số (err, req, res, next) — thiếu một cái là Express coi nó như middleware thường và không bao giờ gọi tới.
  • uncaughtException nghĩa là process đang ở trạng thái không xác định. Đúng bài: ghi log, đóng kết nối, rồi process.exit(1) để orchestrator dựng lại bản sạch.
// ❌ try/catch không với tới callback chạy ở tick sau
try {
  setTimeout(() => { throw new Error('boom'); }, 0);
} catch (e) { console.log('không bao giờ vào đây'); }

// ✅ error middleware của Express: bắt buộc đủ 4 tham số
app.use((err, req, res, next) => {
  logger.error({ err, reqId: req.id });
  res.status(err.status ?? 500).json({ error: 'Lỗi hệ thống' });
});
process.on('unhandledRejection', (reason) => { throw reason; });
process.on('uncaughtException', (err) => {
  logger.fatal({ err });
  process.exit(1);     // ✅ ghi log rồi THOÁT, không chạy tiếp
});
⚠ Bẫy phỏng vấn: Tưởng bắt uncaughtException rồi chạy tiếp là app “sống sót”. Không — nó chỉ giấu lỗi: kết nối có thể đang treo, biến đang dở dang, rò rỉ tích dần. Restart sạch luôn an toàn hơn chạy tiếp trong trạng thái hỏng.
💬 Nói thêm để ghi điểm: Phân biệt operational error (DB timeout, input sai — xử lý rồi trả lỗi cho client) với programmer error (đọc thuộc tính của undefined — để nó nổ và restart). Trộn hai loại này là nguồn gốc của bug khó tìm.
