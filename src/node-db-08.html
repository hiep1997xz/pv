Race condition · Idempotency

💡 Trả lời
  • Lost update: hai request cùng đọc balance ra 100, cùng trừ 30, cùng ghi 70. Trừ hai lần mà chỉ mất 30. Mọi vòng đọc-sửa-ghi ở tầng app đều có khe hở này.
  • Cách rẻ nhất là để DB tự tính: SET balance = balance - $2 kèm điều kiện WHERE balance >= $2. Một câu, nguyên tử, xong. Xem rowCount bằng 0 là biết không đủ tiền.
  • Pessimistic: SELECT ... FOR UPDATE trong transaction khoá dòng lại, request thứ hai phải chờ. Đúng nhưng giảm throughput, và dễ deadlock nếu khoá nhiều dòng khác thứ tự.
  • Optimistic: thêm cột version, update với WHERE id = $1 AND version = $2. rowCount bằng 0 nghĩa là có người sửa trước → đọc lại rồi thử lại. Hợp khi tranh chấp hiếm xảy ra.
  • Unique constraint là chốt chặn cuối và là chốt duy nhất đáng tin. Kiểm tra “đã tồn tại chưa” bằng SELECT rồi mới INSERT vẫn thua race — cứ INSERT rồi bắt mã lỗi 23505.
// ❌ đọc rồi ghi ở tầng app: 2 request song song mất 1 lần trừ
const a = await tx.acc.findUnique({ where: { id } });
await tx.acc.update({ where: { id }, data: { balance: a.balance - n } });

// ✅ pg: để Postgres tự tính — một câu nguyên tử, khỏi cần khoá
const r = await pool.query(
  'UPDATE acc SET balance = balance - $2 WHERE id=$1 AND balance >= $2',
  [id, n]);
if (!r.rowCount) throw new Error('số dư không đủ');

// ✅ idempotency key: lần bấm thứ hai đụng unique index rồi dừng
const p = await pool.query(
  'INSERT INTO pay(key,order_id) VALUES ($1,$2) ON CONFLICT DO NOTHING',
  [idemKey, orderId]);
if (!p.rowCount) return ketQuaCu(idemKey);   // trùng key = đã xử lý
⚠ Bẫy phỏng vấn: Kiểm tra bằng SELECT rồi mới INSERT không bao giờ đúng: hai request cùng SELECT thấy trống, cùng INSERT, ra hai bản ghi. Chỉ unique constraint trong DB mới chặn nổi — code ở tầng app thì không.
💬 Nói thêm để ghi điểm: Idempotency key nên do client sinh (một UUID gắn với lần bấm nút) và gửi qua header, chứ không phải server tự đoán. Lưu luôn kết quả của lần xử lý đầu, để lần gọi lại trả về đúng response cũ thay vì trả lỗi.
