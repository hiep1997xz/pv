Scale · cluster · Graceful shutdown
?cluster và worker_threads khác nhau thế nào?
?Graceful shutdown gồm những bước nào theo thứ tự?
💡 Trả lời
  • cluster fork ra nhiều process, mỗi process một event loop và một vùng nhớ riêng, cùng chia tải trên một cổng. Dùng để tận dụng hết nhân CPU cho tải I/O-bound.
  • worker_threads tạo thread trong cùng process, chia sẻ được bộ nhớ qua SharedArrayBuffer. Dùng cho việc CPU-bound: resize ảnh, nén, hash, tính toán nặng.
  • Chọn sai là mất điểm: việc nặng CPU mà chỉ fork thêm process thì từng process vẫn đơ; việc I/O mà tạo thread thì tốn công vô ích, vì I/O đã bất đồng bộ sẵn.
  • App phải stateless: session, cache, hàng đợi job đẩy ra Redis hay DB. Giữ trong RAM thì mỗi worker một bản khác nhau, scale lên 3 pod là user đăng nhập lúc được lúc không.
  • Graceful shutdown khi nhận SIGTERM: (1) health check trả fail, (2) ngừng nhận kết nối mới, (3) đợi request đang chạy xong, (4) đóng pool DB, (5) hết deadline thì thoát cứng.
import cluster from 'node:cluster';
import { availableParallelism } from 'node:os';
if (cluster.isPrimary) {
  for (let i = 0; i < availableParallelism(); i++) cluster.fork();
  cluster.on('exit', () => cluster.fork());  // worker chết thì dựng lại
} else {
  const server = app.listen(3000);
  process.on('SIGTERM', () => {
    ready = false;                  // ✅ readiness fail trước vài giây
    server.close(async () => {      // ngừng nhận kết nối mới
      await pool.end(); process.exit(0);   // đóng pool DB rồi thoát
    });
    setTimeout(() => process.exit(1), 15_000).unref();  // deadline
  });
}
⚠ Bẫy phỏng vấn: Bỏ qua SIGTERM thì Kubernetes chờ hết grace period rồi SIGKILL: request đang dở bị cắt ngang, transaction treo. Trong Docker, tiến trình Node còn phải là PID 1 hoặc có init, không thì signal chẳng tới nơi.
💬 Nói thêm để ghi điểm: Phân biệt liveness (process còn sống — hỏng thì restart) với readiness (sẵn sàng nhận traffic — hỏng thì chỉ rút khỏi load balancer). Để liveness gọi thẳng vào DB là sai: một hiccup của DB sẽ restart cả cụm.
