Chiến lược test cho frontend
?Bạn phân bổ unit / integration / e2e như thế nào?
?Thế nào là test chi tiết cài đặt?
💡 Trả lời
  • Kim tự tháp cổ điển: nhiều unit, ít e2e. Với frontend, testing trophy (Kent C. Dodds) hợp hơn — phần phình to là integration, vì bug thật hay nằm ở chỗ các mảnh ghép với nhau.
  • Unit cho hàm thuần: reducer, format tiền, validate. Integration render cả màn hình, mock API ở ranh giới network. e2e chỉ vài luồng sinh tiền: đăng nhập, thanh toán.
  • Test hành vi, không test cài đặt: assert cái người dùng thấy, không assert state nội bộ hay số lần hàm private được gọi. Refactor mà test vẫn xanh thì test mới có giá trị.
  • Thứ tự ưu tiên query của Testing Library: getByRole → getByLabelText → getByText, cuối cùng mới getByTestId. Query theo role ép bạn viết markup accessible.
  • Mock ở ranh giới hệ thống (network qua MSW), không mock module nội bộ. Mock càng sâu, test càng tách rời thực tế.
// ❌ test cài đặt: đổi tên biến nội bộ là test đỏ ngay
expect(wrapper.state('isOpen')).toBe(true);
expect(mockFormatTien).toHaveBeenCalledTimes(3);

// ✅ test hành vi: thao tác theo role, assert thứ hiện trên màn hình
await user.click(screen.getByRole('button', { name: /Đặt hàng/ }));
expect(await screen.findByText('Đặt hàng thành công')).toBeVisible();

// ✅ mock ở ranh giới network bằng MSW — code thật giữ nguyên
const server = setupServer(
  http.get('/api/cart', () => HttpResponse.json({ items: [] }))
);
beforeAll(() => server.listen());
afterEach(() => server.resetHandlers());
⚠ Bẫy phỏng vấn: Nói “mục tiêu là 100% coverage” là mất điểm. Coverage chỉ đo dòng code được chạy qua, không đo có assert đúng hay không — test rỗng vẫn cho 100%. Đặt ngưỡng ~80% cho business logic và nói rõ mình bỏ qua config, generated code.
💬 Nói thêm để ghi điểm: Câu chốt đắt giá: “viết test nào mà khi nó đỏ, tôi tin là app thật sự hỏng”. Test flaky còn hại hơn không có test vì team sẽ quen tay retry cho xanh rồi merge.
