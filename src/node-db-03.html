?Làm sao chứng minh được code đang bị N+1?
💡 Trả lời
  • Dấu hiệu: một request bắn ra hàng trăm query gần giống hệt nhau, chỉ khác giá trị id. Thời gian phản hồi tăng tuyến tính theo số dòng — 10 dòng thì mượt, 500 dòng thì treo.
  • Nguyên nhân luôn giống nhau: lấy danh sách xong rồi for / map qua từng phần tử và query tiếp bên trong vòng lặp. 1 query cha + N query con.
  • Cách sửa: eager load (include của Prisma, relations của TypeORM), hoặc tự gom id rồi bắn một câu WHERE id IN (...) và ghép lại bằng Map ở tầng app.
  • GraphQL không sửa được bằng eager load vì resolver chạy theo từng field riêng lẻ → dùng DataLoader: gom các key phát sinh trong cùng một tick rồi bắn một query batch duy nhất.
  • Cách phát hiện: bật log SQL rồi đếm. Prisma dùng log: ['query'], pg thì bọc pool.query. Có số đếm mới nói được “trước 312 query, sau 2 query” — đó mới là câu trả lời ăn điểm.
// ❌ N+1: 1 query lấy posts + 100 query lấy từng author
const posts = await prisma.post.findMany({ take: 100 });
for (const p of posts) {
  p.author = await prisma.user.findUnique({ where: { id: p.userId } });
}

// ✅ cách 1 — eager load, để Prisma tự gom quan hệ
await prisma.post.findMany({ take: 100, include: { author: true } });
// ✅ cách 2 — tự gom id, một câu IN rồi ghép bằng Map
const ids = [...new Set(posts.map(p => p.userId))];
const users = await prisma.user.findMany({
  where: { id: { in: ids } },
});
const byId = new Map(users.map(u => [u.id, u]));
posts.forEach(p => { p.author = byId.get(p.userId); });
⚠ Bẫy phỏng vấn: Bẫy ngược: gộp hết vào một câu JOIN nhiều bảng one-to-many cùng lúc làm bung số dòng (10 post × 50 comment = 500 dòng) rồi phải dedupe ở app. Nhiều khi hai query IN riêng lại nhanh hơn một JOIN to.
💬 Nói thêm để ghi điểm: Chốt bằng con số. Có thể đếm query ngay trong CI: nghe event query của Prisma, cho test fail nếu một endpoint vượt ngưỡng. Như vậy N+1 không lẻn lại được sau mỗi lần refactor.
