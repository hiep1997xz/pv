Message queue · Xử lý bất đồng bộ
?Khi nào nên đẩy việc sang message queue?
?At-least-once và exactly-once khác nhau chỗ nào?
💡 Trả lời
  • Dùng queue cho việc nặng, chậm hoặc được phép trễ: gửi mail, resize ảnh, xuất báo cáo, gọi bên thứ ba. Request trả 202 Accepted ngay, worker làm phần còn lại.
  • Queue còn để giảm chấn: traffic tăng đột biến thì queue phình ra thay vì DB gục. Nhưng queue dài nghĩa là người dùng chờ lâu — phải giám sát consumer lag và cảnh báo sớm.
  • At-least-once là mặc định thực tế: ack sau khi xử lý xong, worker chết giữa chừng thì message được giao lại → có thể trùng. Vì vậy consumer bắt buộc phải idempotent.
  • Exactly-once đầu-cuối gần như không tồn tại. Thứ người ta gọi là exactly-once thường là at-least-once cộng khử trùng theo message id. Nói thẳng điều này rất ghi điểm.
  • DLQ hứng message fail quá số lần retry để không chặn queue chính — phải có alert và công cụ replay. Backpressure: giới hạn prefetch, không kéo message vô hạn về worker.
// ❌ đồng bộ: user ngồi chờ hết mọi việc mới thấy phản hồi
POST /order ─▸ ghi DB ─▸ gọi payment ─▸ gửi mail ─▸ 200  (ví dụ 3.5s)

// ✅ bất đồng bộ: trả về ngay, việc nặng đẩy sang worker
POST /order ─▸ ghi DB ─▸ push 'order.mail' ─▸ 202      (ví dụ 80ms)
                              │
                              ▼
                     ┌────────────────┐
                     │  worker: mail  │──▸ DLQ   // fail quá 3 lần
                     └────────────────┘

// consumer idempotent: message giao lại lần hai cũng vô hại
if (await daXuLy(msg.id)) return ack(msg);
await xuLy(msg); await ghiNhan(msg.id); return ack(msg);
⚠ Bẫy phỏng vấn: Trả lời “dùng Kafka là có exactly-once” là sập bẫy. Hỏi vặn ngay: worker xử lý xong nhưng chết trước khi ack thì sao? → message được giao lại, khách bị trừ tiền hai lần nếu consumer không idempotent.
💬 Nói thêm để ghi điểm: Phân biệt queue và log: RabbitMQ hay SQS lấy message ra là mất, hợp với task. Kafka giữ log theo offset, nhiều consumer group đọc lại được — hợp với event streaming và nhu cầu replay.
