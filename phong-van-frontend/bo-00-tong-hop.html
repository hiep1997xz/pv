React Core

4 câu
Q4 useMemo, useCallback, React.memo — khi nào bạn thực sự dùng? Cho ví dụ từ dự án của bạn. ▸
Gợi ý trả lời

Em không dùng theo phản xạ, vì bản thân 3 cái này cũng có cost (lưu cache, so sánh deps). Em dùng khi có lý do đo được:

  • useMemo: khi tính toán tốn kém trên danh sách lớn. Ví dụ ở PSY HMS có catalog 3.321 đơn vị hành chính, việc build cây tỉnh → huyện → xã và filter theo keyword em memo lại theo [data, keyword], không thì mỗi keystroke re-build cả cây.
  • useCallback: khi function được truyền xuống component con đã memo, hoặc là dependency của useEffect. Ví dụ handler onChange truyền vào từng block trong Template Builder của Offerwall — không memo thì kéo thả 1 block là re-render cả 9 block.
  • React.memo: cho leaf component render nhiều lần với props ổn định. Ví dụ từng cell trong phiếu theo dõi chức năng sống (vital signs) ở PSY — form có hàng trăm input, không memo thì gõ 1 ô là re-render toàn bảng.

Nguyên tắc của em: đo trước, optimize sau — dùng React DevTools Profiler xem component nào re-render và mất bao nhiêu ms, rồi mới thêm memo.

Q5 Form có ~200 input (như phiếu chăm sóc điều dưỡng), gõ 1 ký tự là lag. Bạn debug và fix thế nào? ▸
Gợi ý trả lời

Em làm theo 3 bước:

  1. Xác nhận nguyên nhân — mở React DevTools Profiler, bật "Highlight updates". Nếu cả form sáng lên khi gõ 1 ô → state đang nằm ở component cha và mọi input là controlled từ đó.
  2. Fix gốc: tách subscription. Em dùng react-hook-form — nó là uncontrolled by default (register qua ref), nên gõ 1 ô không trigger re-render form. Chỉ nơi nào cần watch giá trị thì dùng useWatch với name cụ thể, chứ không dùng watch() toàn form. Field array thì dùng useFieldArray, và tách mỗi row ra component riêng + memo.
  3. Nếu vẫn nặng: virtualize phần bảng dài (react-window), và debounce validation nặng (Zod schema có async check) thay vì validate mode onChange — dùng mode: 'onBlur' hoặc onTouched.

Ở PSY em dùng đúng combo Ant Design Form + tách section theo tab/step, mỗi phiếu MOH chia thành các block độc lập, nên không bị re-render chéo.

⚠️

Lưu ý: Đây là câu hỏi "đinh" cho CV của bạn vì bạn khoe form phức tạp. Phải trả lời được mạch: đo → tìm nguyên nhân re-render → chọn uncontrolled → virtualize.

Q6 Giải thích cơ chế reconciliation và vai trò của key. Vì sao dùng index làm key là sai? ▸
Gợi ý trả lời

React so sánh cây Virtual DOM cũ và mới theo từng level. Ở cùng một level, nó dùng key để nhận diện "đây có phải cùng một element không". Cùng type + cùng key → giữ instance, chỉ update props. Khác key → unmount cái cũ, mount cái mới (mất toàn bộ state nội bộ).

Dùng index sai khi list có thể chèn / xóa / sắp xếp lại: xóa item đầu tiên thì item thứ 2 tụt lên index 0, React tưởng nó là item cũ nên giữ nguyên state — dẫn tới giá trị input dính sai row, checkbox tick sai dòng.

Em gặp đúng case này ở Template Builder của Offerwall: 9 loại content block cho phép kéo thả đổi thứ tự và duplicate. Ban đầu dùng index, kéo block xong thì state preview của block bị lẫn. Fix bằng cách mỗi block sinh id riêng (uuid/nanoid) khi tạo và dùng id đó làm key.

Q7 useEffect — kể một bug liên quan đến dependency array bạn từng gặp. ▸
Gợi ý trả lời

Case kinh điển em gặp: infinite loop do object/array trong deps. Ví dụ useEffect(() => fetchList(filter), [filter]) mà filter được tạo mới mỗi render ({ page, keyword } inline) → mỗi lần render tạo object mới → effect chạy lại → setState → render lại → loop.

Cách fix: hoặc để deps là các primitive ([page, keyword]), hoặc useMemo cái filter object, hoặc tốt hơn là không tự fetch trong useEffect — em dùng TanStack Query với queryKey: ['documents', page, keyword], để nó tự lo caching/dedupe/refetch. Từ khi chuyển sang React Query, gần như em không còn viết useEffect để fetch data nữa.

Một case thứ hai là race condition: gõ search nhanh, response cũ về sau response mới → hiển thị sai. Trước em phải tự xử bằng AbortController + cleanup function; giờ React Query xử lý sẵn qua queryKey.

Next.js

3 câu
Q8 Bạn dùng Next.js 11 (SSR, FactoryX), Next 13 (static export, Offerwall), Next 14 App Router (ENAS). So sánh và giải thích vì sao mỗi dự án chọn khác nhau? ▸
Gợi ý trả lời

Mỗi lựa chọn xuất phát từ yêu cầu sản phẩm:

  • FactoryX (Next 11, SSR/getServerSideProps): là platform tuyển dụng thị trường Nhật, trang job listing cần SEO và cần render dữ liệu mới nhất theo từng request → SSR là đúng. Dữ liệu job thay đổi liên tục, không static được.
  • Offerwall (Next 13, static export ra S3/CloudFront): offer wall được nhúng vào app của đối tác, không cần SEO, và hạ tầng yêu cầu deploy tĩnh lên S3 + CDN cho rẻ và scale tốt. Toàn bộ nội dung wall được render động ở client theo config API mà admin cấu hình, nên không cần server render. Trade-off: không dùng được API routes / ISR, mọi thứ phải qua REST API riêng.
  • ENAS (Next 14 App Router): dự án mới nên chọn App Router để dùng Server Components giảm bundle, layout lồng nhau cho khu vực dashboard, và loading/error boundary theo route segment.

Về khác biệt kỹ thuật lớn nhất giữa Pages và App Router: data fetching chuyển từ getServerSideProps/getStaticProps sang async Server Component + fetch với cache option; mặc định component là Server Component, phải khai báo 'use client' khi cần state/effect; và routing convention đổi sang layout.tsx / page.tsx / loading.tsx.

⚠️

Lưu ý: Câu này rất dễ bị hỏi vì CV bạn ghi 3 phiên bản Next khác nhau. Phải nói được "vì sao chọn", không chỉ "em dùng cái gì".

Q9 Server Component vs Client Component — bạn dùng ranh giới nào? Sai lầm thường gặp? ▸
Gợi ý trả lời

Nguyên tắc của em: Server Component là default, 'use client' chỉ đặt ở lá gần nhất cần interactivity. Phần fetch data, đọc secret/token server-side, render nội dung tĩnh → để Server. Phần có state, event handler, hook, browser API → Client.

Sai lầm em từng thấy (và từng mắc):

  1. Đặt 'use client' ở layout.tsx hoặc component cha lớn → toàn bộ cây con thành client, mất hết lợi ích. Fix: đẩy 'use client' xuống component nhỏ nhất, ví dụ chỉ cái button hoặc cái filter.
  2. Truyền function/class instance làm prop từ Server xuống Client → lỗi serialization. Props qua ranh giới phải serializable.
  3. Đưa Ant Design / styled-components vào Server Component → lỗi vì chúng cần context/CSS-in-JS runtime. Với ENAS dùng AntD 5 em phải setup StyleProvider + registry để SSR không bị flash unstyled.
Q10 Hydration mismatch là gì, nguyên nhân phổ biến, cách xử? ▸
Gợi ý trả lời

Là khi HTML server render ra khác với cây React client render lần đầu, React cảnh báo và có thể render lại/bỏ HTML server.

Nguyên nhân hay gặp: dùng Date.now() / new Date() / Math.random() trong render; đọc localStorage hoặc window khi render; render theo theme dark/light lưu ở client; format ngày theo timezone của máy (dự án Nhật — server UTC, client JST → lệch ngày).

Cách xử của em: giá trị chỉ có ở client thì render sau khi mount (useEffect set state, lần đầu render placeholder), hoặc dùng dynamic(..., { ssr: false }); với timezone thì format ở một chỗ duy nhất, ép timezone rõ ràng (Asia/Tokyo) thay vì dựa vào locale máy. Ở FactoryX dự án Nhật em luôn chuẩn hóa: BE trả UTC ISO string, FE format theo timezone cố định của nghiệp vụ.

03

State Management & Data Fetching

3 câu
Q11 Bạn dùng cả Redux Toolkit, Zustand và TanStack Query. Tiêu chí chọn? ▸
Gợi ý trả lời

Em phân biệt rõ server state và client state — đây là điểm quan trọng nhất:

  • Server state (data từ API): luôn dùng TanStack Query. Nó lo cache theo queryKey, dedupe request, stale-while-revalidate, retry, invalidate sau mutation. Trước đây nhiều dự án nhét API data vào Redux, dẫn tới viết tay 3 action loading/success/error cho mỗi endpoint — rất nhiều boilerplate và cache tự quản lý rất dễ sai.
  • Client state nhỏ, cục bộ (UI toggle, filter, step của wizard): Zustand. Nhẹ, không cần Provider, API đơn giản, chọn selector để tránh re-render. Em dùng Zustand ở Offerwall, FactoryX, PSY HMS.
  • Redux Toolkit: dùng khi dự án đã có sẵn (ENAS, WAS) hoặc khi state phức tạp cần devtools time-travel, middleware, nhiều slice liên quan chặt. Nếu bắt đầu mới và không cần những thứ đó, em chọn Zustand + React Query.

Thực tế ở PSY HMS: server state qua TanStack Query, còn Zustand chỉ giữ auth/permission matrix và trạng thái UI của form nhiều bước.

Q12 Giải thích staleTime vs gcTime (cacheTime) trong TanStack Query. Bạn set thế nào? ▸
Gợi ý trả lời
  • staleTime: khoảng thời gian data còn được coi là "tươi". Trong khoảng này, mount lại component hoặc focus lại window không refetch, dùng luôn cache. Default là 0 → luôn refetch background.
  • gcTime: sau khi query không còn observer nào (component unmount), cache còn được giữ bao lâu trước khi bị xóa. Default 5 phút. Nó quyết định việc quay lại trang có hiện data cũ ngay lập tức hay hiện loading.

Cách em set theo tính chất dữ liệu:

  • Catalog / danh mục ít đổi (ICD-10, danh mục thuốc, 3.321 đơn vị hành chính ở PSY): staleTime rất dài, 30 phút đến Infinity, vì gần như không đổi trong một session.
  • Dữ liệu nghiệp vụ đang thao tác (danh sách bệnh nhân, đơn thuốc chờ duyệt): staleTime ngắn 0–30s để luôn mới, và invalidateQueries ngay sau mutation.
  • Dashboard / báo cáo: staleTime vài phút, thêm refetchOnWindowFocus: false để không nhấp nháy khi user switch tab.
Q13 Sau khi tạo/sửa một record, làm sao list được cập nhật? So sánh invalidate vs optimistic update. ▸
Gợi ý trả lời

Hai cách em dùng:

  1. Invalidate (mặc định, an toàn): trong onSuccess của mutation gọi queryClient.invalidateQueries({ queryKey: ['prescriptions'] }). Data sẽ refetch từ server → chắc chắn đúng. Trade-off: user thấy một nhịp loading nhỏ.
  2. Optimistic update: trong onMutate cập nhật cache ngay (setQueryData), lưu snapshot; nếu lỗi thì onError rollback về snapshot; onSettled invalidate để đồng bộ lại. Dùng khi cần UI phản hồi tức thì và rủi ro thất bại thấp — ví dụ toggle trạng thái bật/tắt banner, đổi thứ tự block trong Template Builder (kéo thả phải mượt, không thể chờ API).

Với nghiệp vụ y tế ở PSY thì em không optimistic cho các hành động quan trọng như duyệt đơn thuốc hay xuất kho — sai số liệu ở đó nguy hiểm, nên em chọn invalidate + loading rõ ràng, thà chậm 300ms còn hơn hiển thị sai tồn kho.

Kiến trúc & Bài toán khó trong CV

5 câu
Q14 Kể chi tiết về schema-driven dynamic form engine ở ENAS. Bạn thiết kế kiến trúc thế nào? ▸
Gợi ý trả lời

Bài toán: khách hàng (doanh nghiệp Nhật) tự tạo form thu lead bằng drag-and-drop, có validation phức tạp và tối ưu EFO (Entry Form Optimization). Nghĩa là form không hard-code mà phải render từ dữ liệu.

Em tách thành 4 layer rõ ràng:

  1. Schema layer — nguồn sự thật duy nhất: một JSON mô tả các field (type, label, required, rule validate, điều kiện hiển thị). Đây là thứ lưu DB và render cả ở builder lẫn form public.
  2. Converter layer — chuyển schema ↔ format API, và sinh validation schema (Zod/Yup) từ rule trong schema. Tách riêng để khi BE đổi shape thì chỉ sửa một chỗ.
  3. Layout layer — lo grid, thứ tự, group field, responsive. Không biết gì về UI cụ thể.
  4. UI layer — map type → component thực tế qua một registry ({ text: TextInput, select: SelectInput, ... }). Thêm loại field mới = thêm 1 entry vào registry + 1 rule ở converter, không sửa core.

Lợi ích rõ nhất: khi PO yêu cầu thêm field type mới (ví dụ postal-code auto-fill địa chỉ — rất phổ biến ở Nhật), em chỉ thêm component + rule, không phải đụng vào engine. EFO features (auto-focus field kế tiếp, realtime validate, hiện progress) được implement một lần ở layout/engine và áp dụng cho mọi form.

⭐

Lưu ý: Đây là câu ăn điểm nhất của bạn. Hãy vẽ được 4 layer trên giấy/whiteboard khi trả lời. Nhấn vào từ khóa registry pattern và "thêm field mới không sửa core" (Open/Closed Principle).

Q15 Template Builder (Offerwall) và Process Diagram Editor (ReactFlow) — khó nhất ở đâu? ▸
Gợi ý trả lời

Template Builder (Offerwall): 9 loại content block, kéo thả đổi thứ tự, duplicate, preview live trong khung điện thoại. Ba cái khó:

  1. Đồng bộ editor ↔ preview: preview phải dùng đúng component mà offer wall public dùng, nếu viết 2 bản sẽ lệch. Em giải quyết bằng cách dùng chung một bộ renderer, chỉ khác wrapper (khung phone + disable interaction).
  2. Identity của block: mỗi block phải có id riêng sinh lúc tạo, không dùng index, không thì duplicate/reorder là lẫn state.
  3. Performance khi kéo: kéo thả trigger update liên tục. Em giữ state kéo thả cục bộ trong lúc drag, chỉ commit vào store khi drop; đồng thời memo từng block để không re-render cả 9 block mỗi frame.

Process Editor (ReactFlow, Bidding Assistant): khó ở chỗ đây là quy trình đấu thầu có stage và nhóm quy trình, cần validate tính hợp lệ của graph — không cho tạo cycle, không cho node treo không có kết nối. Em viết validate ở tầng domain (duyệt graph tìm cycle) chứ không nhét vào component; và lưu layout (vị trí node) cùng với quan hệ logic để mở lại đúng như lúc lưu.

Q16 RBAC với 6 role và permission matrix chi tiết (PSY) — bạn làm ở FE thế nào? FE check quyền là đủ chưa? ▸

Ở FE em làm 3 tầng:

  1. Nguồn quyền: sau login, BE trả về danh sách permission dạng resource:action (ví dụ prescription:approve, inventory:export). Em lưu vào store (Zustand) và expose một hook useCan('prescription:approve').

Q17 Upload và parse file DOCX/PDF lên S3-compatible (RustFS). Bạn xử lý file lớn, progress, lỗi thế nào? ▸
Gợi ý trả lời

Luồng em làm ở Bidding Assistant:

  2. Presigned URL: FE xin presigned PUT URL từ BE rồi upload trực tiếp lên storage, không đi qua app server. Giảm tải server và không bị giới hạn body size của API.

Q21 type vs interface? any vs unknown? Bạn xử lý type của API response thế nào? ▸

CI/CD, Docker & Fullstack

3 câu
Q22 Bạn set up Jenkins pipeline với Docker. Mô tả pipeline đó. ▸
Gợi ý trả lời

Pipeline em dựng ở IniSoft (Jenkinsfile, declarative) gồm các stage:

  1. Checkout — theo branch, webhook từ GitLab trigger.
  2. Install & Cache — pnpm install --frozen-lockfile, cache node_modules / pnpm store giữa các build cho nhanh.
  3. Quality gate — lint, typecheck (tsc --noEmit), unit test (Vitest + React Testing Library ở PSY). Fail là dừng, không cho deploy.
  4. Build — multi-stage Dockerfile: stage builder chạy pnpm build, stage runtime chỉ copy dist vào nginx alpine → image nhỏ, không chứa devDependencies và source.
  5. Push image — tag theo git SHA + version, đẩy lên registry. Tag theo SHA để rollback được chính xác.
  6. Deploy — docker-compose up -d trên server theo môi trường (dev/staging), production thì có bước approval thủ công.

Vài điểm em chú ý: build args cho env public (VITE_*) vì Vite inline biến lúc build — nên mỗi môi trường phải build riêng hoặc runtime-inject config; secret không để trong ENV của Dockerfile (nó nằm trong image history), mà lấy từ Jenkins credentials; và Dockerfile chạy user non-root.

Gợi ý trả lời
  1. Đánh giá trước, sửa sau: bug này ảnh hưởng ai, bao nhiêu %, có mất/sai dữ liệu không, có workaround không. Ở PSY mà bug liên quan tới đơn thuốc hoặc tồn kho thuốc thì mặc định là blocker — sai số liệu y tế là không thể release.
  2. Báo ngay cho lead/PO kèm thông tin đủ để họ quyết định: mức độ ảnh hưởng, nguyên nhân (nếu đã biết), thời gian fix dự kiến, rủi ro nếu fix gấp.
  3. Đề xuất phương án, không chỉ báo vấn đề: (a) hotfix nếu nguyên nhân rõ và fix nhỏ, (b) tắt tính năng đó bằng feature flag và release phần còn lại, (c) hoãn release.
  4. Fix thì fix tối thiểu — không refactor kèm theo lúc gần release. Viết test cho case đó để không tái diễn.
  5. Sau release: retro ngắn — vì sao QA phát hiện muộn, có thiếu test case nào không, thêm vào checklist.

Điều em tránh: im lặng tự fix đến đêm rồi đẩy lên mà không ai biết. Quyết định release là của lead/PO, việc của em là cung cấp thông tin chính xác và nhanh.

Q32 Bạn được giao maintain một codebase legacy không có document, không test, code rối. Bắt đầu từ đâu? ▸
Gợi ý trả lời

Em từng ở tình huống gần giống khi nhận tiếp module ở Offerwall và WAS.

  1. Chạy được trước đã — setup local, đi hết luồng chính bằng tay để hiểu sản phẩm làm gì. Hiểu nghiệp vụ trước khi đọc code.
  2. Vẽ map — đâu là entry point, routing, nơi gọi API, nơi giữ state. Em thường note lại thành một file map ngắn, vì chính em 2 tuần sau cũng cần.
  3. Không refactor ngay. Refactor code mình chưa hiểu, không có test bảo vệ, là cách nhanh nhất để tạo bug. Em làm task thật trước, mỗi task hiểu thêm một vùng.
  4. Thêm an toàn dần: trước khi sửa một vùng, viết test cho hành vi hiện tại (characterization test), rồi mới đổi. Bật dần TypeScript strict / lint theo từng folder thay vì bật cả repo rồi ngập 2000 lỗi.
  5. Refactor theo cơ hội — chỗ nào mình đang phải sửa thì dọn chỗ đó (boy scout rule), không mở PR refactor 50 file.

Câu bạn nên hỏi lại nhà tuyển dụng

Phần này rất quan trọng — không hỏi gì là mất điểm. Chọn 3–4 câu:

  • Team frontend hiện có bao nhiêu người, và vị trí này sẽ own phần nào của sản phẩm?
  • Codebase hiện tại dùng stack gì, có test coverage và CI/CD chưa? Nợ kỹ thuật lớn nhất hiện nay là gì?
  • Quy trình từ lúc có yêu cầu đến khi release như thế nào? Có QA riêng không, có code review bắt buộc không?
  • Sản phẩm có bao nhiêu người dùng / traffic cỡ nào? (để biết bài toán performance có thật hay không)
  • Lộ trình phát triển cho vị trí này trong 1–2 năm tới là gì? Có định hướng lên Senior/Lead không?
  • Có phải làm việc trực tiếp với client nước ngoài không? Yêu cầu ngoại ngữ ở mức nào?

Điểm mạnh cần đẩy mạnh trong phỏng vấn

  • Breadth thật: React 17→19, Next 11/13/14, cả Vite SPA, cả monorepo pnpm
  • Bài toán khó cụ thể: schema-driven form engine, drag-drop builder, ReactFlow, RBAC 6 role

  • Domain đa dạng: y tế (MOH standard), quảng cáo, SaaS Nhật, AI/RAG
