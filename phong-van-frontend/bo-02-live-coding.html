3 câu
Q1 Viết hàm debounce thuần, rồi bọc thành hook useDebouncedValue. ▸
Đề bài người phỏng vấn đưa ra

Yêu cầu: debounce(fn, delay) trả về hàm mới; gọi liên tục thì chỉ chạy sau khi ngừng delayms. Có cancel(). Sau đó làm hook để dùng cho ô search.

Gợi ý trả lời

Bước 1 — hàm thuần. Điểm phải nói: giữ this, forward mọi tham số, và cho phép huỷ.

function debounce(fn, delay = 300) {
  let timer = null;

  function debounced(...args) {
    if (timer) clearTimeout(timer);
    timer = setTimeout(() => {
      timer = null;
      fn.apply(this, args);
    }, delay);
  }

  debounced.cancel = () => {
    if (timer) clearTimeout(timer);
    timer = null;
  };

  return debounced;
}

Bước 2 — hook. Trong React em thường debounce giá trị chứ không debounce callback, vì debounce callback dễ bị tạo lại mỗi render và mất timer.

function useDebouncedValue(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);   // cleanup chính là phần "debounce"
  }, [value, delay]);

  return debounced;
}

// dùng:
const [keyword, setKeyword] = useState('');
const q = useDebouncedValue(keyword, 350);
const { data } = useQuery({ queryKey: ['patients', q], queryFn: () => search(q) });

Edge case cần tự nêu: (1) input vẫn phải cập nhật tức thì để user thấy mình gõ được — nên tách keyword (hiển thị) và q (gọi API); (2) khi user xoá hết thì nên bỏ debounce để reset danh sách ngay; (3) nếu debounce callback thì phải useMemo nó và cancel() trong cleanup, không thì unmount xong timer vẫn chạy.

⭐

Điểm ăn tiền: Nếu bạn nói được "trong React em debounce giá trị chứ không debounce hàm, vì cleanup của useEffect đã là cơ chế debounce sẵn" — đó là dấu hiệu của người làm thật, không phải học vở.

Q2 Viết hook useFetch(url) tự xử lý race condition và cancel khi unmount. ▸
Đề bài người phỏng vấn đưa ra

Trả về { data, error, loading }. Gõ search nhanh thì response cũ về sau response mới không được ghi đè dữ liệu mới.

Gợi ý trả lời 
function useFetch(url) {
  const [state, setState] = useState({ data: null, error: null, loading: true });

  useEffect(() => {
    const controller = new AbortController();
    let alive = true;                 // chốt thứ hai, phòng khi abort không kịp

    setState(s => ({ ...s, loading: true, error: null }));

    fetch(url, { signal: controller.signal })
      .then(res => {
        if (!res.ok) throw new Error('HTTP ' + res.status);
        return res.json();
      })
      .then(data => {
        if (alive) setState({ data, error: null, loading: false });
      })
      .catch(err => {
        if (err.name === 'AbortError') return;      // huỷ chủ động, không phải lỗi
        if (alive) setState({ data: null, error: err, loading: false });
      });

    return () => {
      alive = false;
      controller.abort();      // url đổi hoặc unmount -> huỷ request cũ
    };
  }, [url]);

  return state;
}

Ba điểm phải nói ra:

  1. Cleanup chạy trước effect mới — nên request cũ bị abort trước khi request mới bắt đầu. Đó chính là cách chặn race condition.
  2. AbortError không phải lỗi thật — phải lọc, không thì UI hiện "Có lỗi" mỗi lần user gõ tiếp.
  3. fetch không throw khi 4xx/5xx — phải tự check res.ok. Đây là bug rất hay gặp.

Và câu chốt ăn điểm: "Trong dự án thật em không tự viết hook này — em dùng TanStack Query, vì nó lo sẵn cache, dedupe, retry, và race condition qua queryKey. Em viết tay ở đây để thể hiện là em hiểu bên dưới nó làm gì."

Q3 Viết useCan + component <Can> cho hệ thống RBAC 6 role (như PSY HMS). ▸
Đề bài người phỏng vấn đưa ra

BE trả về sau khi login: permissions: ['prescription:read', 'prescription:approve', 'inventory:*']. Cần hook kiểm tra quyền, hỗ trợ wildcard, và component bọc UI.

Gợi ý trả lời 
// store — Zustand
const useAuthStore = create((set) => ({
  permissions: [],
  setPermissions: (permissions) => set({ permissions }),
}));

// So khớp có wildcard: 'inventory:*' khớp 'inventory:export'
function matches(granted, required) {
  if (granted === '*' || granted === required) return true;
  const [gRes, gAct] = granted.split(':');
  const [rRes, rAct] = required.split(':');
  return (gRes === '*' || gRes === rRes) && (gAct === '*' || gAct === rAct);
}

export function useCan() {
  const permissions = useAuthStore(s => s.permissions);

  // Set + useCallback: tra cứu O(1) cho khớp chính xác, chỉ fallback loop khi có wildcard
  return useMemo(() => {
    const exact = new Set(permissions);
    const wild  = permissions.filter(p => p.includes('*'));

    return (required) => {
      if (!required) return true;
      const list = Array.isArray(required) ? required : [required];
      return list.every(r => exact.has(r) || wild.some(w => matches(w, r)));
    };
  }, [permissions]);
}

// Component bọc UI
export function Can({ permission, fallback = null, children }) {
  const can = useCan();
  return can(permission) ? children : fallback;
}
// dùng
const can = useCan();

<Can permission="prescription:approve">
  <Button onClick={approve}>Duyệt đơn</Button>
</Can>

// hoặc disable kèm lý do, thường UX tốt hơn là ẩn hẳn
<Tooltip title={can('inventory:export') ? '' : 'Bạn không có quyền xuất kho'}>
  <Button disabled={!can('inventory:export')}>Xuất kho</Button>
</Tooltip>

Phải nói thêm 3 điều — đây là phần phân biệt Middle với Junior:

  1. FE check quyền chỉ là UX, không phải bảo mật. BE bắt buộc enforce lại ở từng endpoint, nếu không mở DevTools là bypass.
  2. Check theo permission, không theo role. role === 'doctor' rải khắp code thì thêm role mới là sửa hàng chục chỗ.
  3. Route guard và menu phải đọc cùng một config — không thì menu hiện mục mà vào bị 403, hoặc ngược lại.
⭐

Điểm ăn tiền: Bài này gắn trực tiếp với dự án PSY HMS trong CV bạn. Nếu người phỏng vấn không đưa bài này, bạn có thể tự kể như ví dụ khi họ hỏi về RBAC.

Q4 Từ danh sách phẳng có parentId, dựng cây và render comment lồng nhau. ▸
Đề bài người phỏng vấn đưa ra

[{ id: 3, parentId: 1, text: '...' }, ...] — hàng nghìn phần tử. Dựng cây rồi render đệ quy. Chú ý hiệu năng.

Gợi ý trả lời

Dựng cây một lượt, O(n) — đừng dùng filter lồng trong map vì đó là O(n²):

function buildTree(items) {
  const byId = new Map();
  const roots = [];

  // lượt 1: tạo node, khởi tạo children
  for (const item of items) {
    byId.set(item.id, { ...item, children: [] });
  }

  // lượt 2: nối vào cha
  for (const item of items) {
    const node = byId.get(item.id);
    if (item.parentId == null) {
      roots.push(node);
    } else {
      const parent = byId.get(item.parentId);
      if (parent) parent.children.push(node);
      else roots.push(node);        // cha bị xoá -> coi như gốc, đừng để mất dữ liệu
    }
  }

  return roots;
}
const Comment = memo(function Comment({ node, depth = 0 }) {
  return (
    <li style={{ marginLeft: depth * 16 }}>
      {node.text}
      {node.children.length > 0 && (
        <ul>
          {node.children.map(child => (
            <Comment key={child.id} node={child} depth={depth + 1} />
          ))}
        </ul>
      )}
    </li>
  );
});

// trong component cha
const tree = useMemo(() => buildTree(items), [items]);

Edge case tự nêu (đây là điểm cộng lớn):

  • Cha mất (bị xoá / chưa load): đẩy lên gốc chứ không im lặng bỏ — mất dữ liệu là bug tệ nhất.
  • Vòng lặp (A là cha B, B là cha A — dữ liệu bẩn): render đệ quy sẽ tràn stack. Thêm Set các id đã thăm, hoặc giới hạn depth tối đa.
  • Cây quá sâu: giới hạn hiển thị ~5 cấp rồi nút "Xem thêm trả lời" — Reddit, Facebook đều làm vậy, vừa gọn vừa tránh tràn stack.
  • Cây rất lớn: đệ quy React render hết một lượt. Cần thì chuyển sang flatten có depth + virtualize, vì virtualize không làm được trên cây lồng DOM.
  • key phải là id, không phải index — xoá 1 comment là lệch toàn bộ state con.
Q5 Viết virtual list đơn giản cho 50.000 dòng cao bằng nhau. ▸
Đề bài người phỏng vấn đưa ra

Không dùng thư viện. Container cao 600px, mỗi dòng 40px. Chỉ render phần trong viewport.

Gợi ý trả lời 
function VirtualList({ items, rowHeight = 40, height = 600, overscan = 3 }) {
  const [scrollTop, setScrollTop] = useState(0);

  const total       = items.length * rowHeight;
  const visibleRows = Math.ceil(height / rowHeight);

  // chỉ số bắt đầu/kết thúc, cộng thêm overscan để không thấy khoảng trắng khi scroll nhanh
  const start = Math.max(0, Math.floor(scrollTop / rowHeight) - overscan);
  const end   = Math.min(items.length, start + visibleRows + overscan * 2);

  const slice = items.slice(start, end);

  return (
    <div
      style={{ height, overflowY: 'auto', position: 'relative' }}
      onScroll={e => setScrollTop(e.currentTarget.scrollTop)}
    >
      {/* lớp giữ chiều cao thật để scrollbar đúng tỉ lệ */}
      <div style={{ height: total, position: 'relative' }}>
        {slice.map((item, i) => {
          const index = start + i;
          return (
            <div
              key={item.id}
              style={{
                position: 'absolute',
                top: index * rowHeight,
                height: rowHeight,
                left: 0, right: 0,
              }}
            >
              {item.name}
            </div>
          );
        })}
      </div>
    </div>
  );
}

Ý tưởng cốt lõi để nói ra: một div "spacer" cao n × rowHeight để scrollbar đúng, còn các dòng thì position: absolute đặt đúng offset. DOM chỉ giữ ~20 node thay vì 50.000.

Giới hạn và bước tiếp theo — nên tự nêu:

  • onScroll setState mỗi frame là hơi nặng: dùng transform: translateY trên một wrapper thay vì top tuyệt đối, hoặc throttle theo requestAnimationFrame.
  • Dòng cao không đều là bài toán khó hơn nhiều: phải đo thật (ResizeObserver) và giữ bảng offset tích luỹ. Lúc này em dùng TanStack Virtual chứ không tự viết.
  • Accessibility: virtual list phá Ctrl+F của browser và screen reader không thấy dòng chưa render — cần aria-rowcount/aria-rowindex nếu là bảng.
  • Thực tế ở dự án em: với bảng admin 10.000 dòng em ưu tiên server-side pagination trước, virtualize chỉ dùng khi nghiệp vụ bắt buộc scroll liên tục — như infinite scroll của offer wall.

Q6 Viết Modal accessible: focus trap, Esc để đóng, trả focus về nút đã mở, portal. ▸
Đề bài người phỏng vấn đưa ra

Không dùng Ant Design / Radix. Phải dùng được bằng bàn phím và screen reader.

Gợi ý trả lời 
function Modal({ open, onClose, title, children }) {
  const panelRef   = useRef(null);
  const restoreRef = useRef(null);

  // Nhớ element đang focus để trả lại khi đóng
  useEffect(() => {
    if (open) restoreRef.current = document.activeElement;
    else restoreRef.current?.focus?.();
  }, [open]);

  useEffect(() => {
    if (!open) return;

    // focus vào panel khi mở
    panelRef.current?.focus();

    function onKeyDown(e) {
      if (e.key === 'Escape') { onClose(); return; }
      if (e.key !== 'Tab') return;

      // focus trap: vòng Tab trong panel
      const nodes = panelRef.current.querySelectorAll(
        'a[href], button:not([disabled]), input:not([disabled]), select, textarea, [tabindex]:not([tabindex="-1"])'
      );
      if (nodes.length === 0) return;

      const first = nodes[0];
      const last  = nodes[nodes.length - 1];

      if (e.shiftKey && document.activeElement === first) {
        e.preventDefault(); last.focus();
      } else if (!e.shiftKey && document.activeElement === last) {
        e.preventDefault(); first.focus();
      }
    }

    document.addEventListener('keydown', onKeyDown);
    // chặn scroll trang phía sau
    const prevOverflow = document.body.style.overflow;
    document.body.style.overflow = 'hidden';

    return () => {
      document.removeEventListener('keydown', onKeyDown);
      document.body.style.overflow = prevOverflow;
    };
  }, [open, onClose]);

  if (!open) return null;

  return createPortal(
    <div className="overlay" onMouseDown={onClose}>
      <div
        ref={panelRef}
        className="panel"
        role="dialog"
        aria-modal="true"
        aria-labelledby="modal-title"
        tabIndex={-1}
        onMouseDown={e => e.stopPropagation()}   // click trong panel không đóng
      >
        <h2 id="modal-title">{title}</h2>
        {children}
      </div>
    </div>,
    document.body
  );
}

Checklist a11y phải kể ra: role="dialog" + aria-modal="true" + aria-labelledby trỏ vào tiêu đề · Esc đóng · Tab không thoát ra ngoài · trả focus về nút đã mở (rất hay bị bỏ) · portal ra body để thoát stacking context và overflow: hidden của cha · chặn scroll nền · click overlay đóng nhưng click nội dung thì không (dùng onMouseDown + stopPropagation, không phải onClick, để tránh đóng khi user bôi đen text kéo ra ngoài).

Thiếu sót còn lại nên tự thừa nhận: chưa xử lý nhiều modal xếp lớp (cần stack + chỉ modal trên cùng nhận Esc), và chưa inert phần nền cho screen reader.

💡

Mẹo: A11y là chỗ đa số ứng viên FE Việt Nam bỏ trống. Chỉ cần bạn nhắc được "trả focus về nút đã mở" và aria-modal là đã nổi bật.

Q7 Viết retryWithBackoff — retry có exponential backoff + jitter, chỉ retry lỗi tạm thời. ▸
Đề bài người phỏng vấn đưa ra

Dùng cho API upload tài liệu (dự án Bidding Assistant). Retry tối đa 3 lần, không retry 4xx.

Gợi ý trả lời 
class HttpError extends Error {
  constructor(status, message) { super(message); this.status = status; }
}

// Chỉ lỗi tạm thời mới đáng retry
function isRetryable(err) {
  if (err instanceof HttpError) {
    return err.status === 429 || err.status >= 500;
  }
  return true;   // lỗi network / timeout
}

const sleep = (ms, signal) => new Promise((resolve, reject) => {
  const id = setTimeout(resolve, ms);
  signal?.addEventListener('abort', () => { clearTimeout(id); reject(new Error('aborted')); },
    { once: true });
});

async function retryWithBackoff(fn, { retries = 3, base = 500, cap = 8000, signal } = {}) {
  let lastErr;

  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      return await fn({ attempt, signal });
    } catch (err) {
      lastErr = err;

      if (attempt === retries || !isRetryable(err)) throw err;

      // exponential: 500, 1000, 2000... chặn trần ở cap
      const backoff = Math.min(cap, base * 2 ** attempt);
      // full jitter: tránh mọi client retry cùng lúc (thundering herd)
      const delay = Math.random() * backoff;

      await sleep(delay, signal);
    }
  }

  throw lastErr;
}

Bốn điểm phải giải thích:

  1. Vì sao exponential: server đang quá tải, retry dày chỉ làm nó tệ hơn.
  2. Vì sao jitter: nếu 1.000 client cùng fail và cùng retry sau đúng 1s, chúng lại đập server cùng lúc — jitter tán chúng ra.
  3. Vì sao có cap: không để delay leo lên hàng phút, user sẽ nghĩ app treo.
  4. Vì sao không retry 4xx: 400/422 là lỗi dữ liệu, retry 3 lần vẫn sai — chỉ tốn thời gian của user. 401 thì phải refresh token, không phải retry.

Và cảnh báo quan trọng: chỉ retry request idempotent. Retry một POST tạo đơn thuốc có thể tạo 2 đơn. Muốn retry POST thì phải có idempotency key do client sinh và BE tôn trọng. Ở PSY HMS em tắt retry cho mọi mutation ghi dữ liệu y tế đúng vì lý do này.

Q8 Đoạn code này có 4 bug. Tìm và sửa. ▸
Đề bài người phỏng vấn đưa ra
function TodoList({ userId }) {
  const [todos, setTodos] = useState([]);
  const [filter, setFilter] = useState({ done: false });

  useEffect(() => {
    fetch('/api/todos?user=' + userId)
      .then(r => r.json())
      .then(setTodos);
  }, [filter]);

  const visible = todos.filter(t => t.done === filter.done);

  return (
    <ul>
      {visible.map((todo, i) => (
        <li key={i}>
          <input defaultValue={todo.title} />
          <button onClick={() => {
            todos.splice(i, 1);
            setTodos(todos);
          }}>Xoá</button>
        </li>
      ))}
    </ul>
  );
}
Đáp án — 4 bug

Bug 1 — deps sai. Effect fetch theo userId nhưng deps là [filter]. Đổi userId thì không fetch lại (hiện dữ liệu người cũ); đổi filter thì fetch lại vô ích. Tệ hơn: filter là object nên nếu cha tạo mới mỗi render là vòng lặp vô hạn.

Bug 2 — mutate state trực tiếp. todos.splice() sửa chính mảng trong state rồi setTodos(todos) truyền lại cùng một reference → React so sánh thấy không đổi → không re-render. Phải tạo mảng mới.

Bug 3 — key={i}. List có xoá phần tử. Xoá dòng 0 thì dòng 1 tụt lên index 0, React tưởng là cùng element nên giữ nguyên DOM — defaultValue của input không được cập nhật, giá trị dính sai dòng.

Bug 4 — index lệch. i là index trong visible (đã filter), nhưng splice(i, 1) áp lên todos (chưa filter) → xoá sai phần tử. Phải xoá theo id.

Bonus bug 5: không có catch, không xử lý loading/error, và không có race-condition guard khi userId đổi nhanh.

Bản đã sửa:

function TodoList({ userId }) {
  const [filter, setFilter] = useState({ done: false });

  // Dùng React Query: queryKey lo cache + race condition, không cần useEffect
  const { data: todos = [], isLoading, error } = useQuery({
    queryKey: ['todos', userId],
    queryFn: ({ signal }) =>
      fetch(`/api/todos?user=${userId}`, { signal }).then(r => {
        if (!r.ok) throw new Error('HTTP ' + r.status);
        return r.json();
      }),
  });

  const [removed, setRemoved] = useState([]);   // ví dụ đơn giản; thực tế dùng mutation
  const visible = useMemo(
    () => todos.filter(t => t.done === filter.done && !removed.includes(t.id)),
    [todos, filter.done, removed]
  );

  if (isLoading) return <Spinner />;
  if (error)     return <ErrorState error={error} />;

  return (
    <ul>
      {visible.map(todo => (
        <li key={todo.id}>                                {/* key theo id */}
          <input defaultValue={todo.title} />
          <button onClick={() => setRemoved(prev => [...prev, todo.id])}>  {/* mảng mới, theo id */}
            Xoá
          </button>
        </li>
      ))}
    </ul>
  );
}

Điểm ăn tiền: Bài "tìm bug" rất hay được dùng. Hãy đọc to từng dòng và nói ra suy luận — người phỏng vấn chấm quy trình rà soát của bạn, không chỉ số bug tìm được.

Q9 Format ngày và tiền cho hệ thống Nhật. Code hiện tại lệch ngày 1 hôm — sửa. ▸
Đề bài người phỏng vấn đưa ra

BE trả createdAt: '2026-03-15T22:30:00Z'. Nghiệp vụ tính theo giờ Nhật (JST, UTC+9). Máy dev ở Việt Nam (UTC+7) hiện 15/03, server hiện 15/03, nhưng khách Nhật phải thấy 16/03.

Gợi ý trả lời

Nguyên nhân: mọi API format ngày dựa vào timezone của máy đang chạy. 22:30 UTC = 05:30 ngày 16 ở Nhật, nhưng = 05:30 ngày 16 ở VN thì... thực ra là 05:30 ngày 16 (UTC+7) — sai lệch xuất hiện rõ nhất với mốc quanh nửa đêm và khi so sánh "hôm nay". Vấn đề gốc: không ép timezone nghiệp vụ, để browser tự quyết.

// ❌ SAI: phụ thuộc timezone máy chạy
new Date(iso).toLocaleDateString();
new Date(iso).getDate();               // ngày theo máy, không phải theo JST

// ✅ ĐÚNG: ép timezone nghiệp vụ, khai báo rõ ràng
const JP_DATE = new Intl.DateTimeFormat('ja-JP', {
  timeZone: 'Asia/Tokyo',
  year: 'numeric', month: '2-digit', day: '2-digit',
});

const JP_DATETIME = new Intl.DateTimeFormat('ja-JP', {
  timeZone: 'Asia/Tokyo',
  dateStyle: 'medium', timeStyle: 'short',
});

export const formatDateJP     = (iso) => JP_DATE.format(new Date(iso));
export const formatDateTimeJP = (iso) => JP_DATETIME.format(new Date(iso));

// Tiền: dùng Intl, không tự nối 'đ' hay '¥'
const JPY = new Intl.NumberFormat('ja-JP', {
  style: 'currency', currency: 'JPY', maximumFractionDigits: 0,   // yên không có số lẻ
});
const VND = new Intl.NumberFormat('vi-VN', {
  style: 'currency', currency: 'VND', maximumFractionDigits: 0,
});

Quy ước em áp dụng trong dự án (nói ra phần này mới ăn điểm):

  1. BE luôn trả UTC ISO string có hậu tố Z. Không bao giờ trả '2026-03-15 22:30:00' không timezone — đó là nguồn của mọi bug lệch giờ.
  2. FE có đúng một module format (utils/datetime.ts), không ai được gọi toLocaleDateString() rải rác. Lint rule ban toLocaleDateString nếu cần.
  3. Timezone nghiệp vụ là cấu hình, không hard-code — hệ thống Nhật thì Asia/Tokyo, hệ thống bệnh viện VN thì Asia/Ho_Chi_Minh.
  4. Ngày không có giờ (ngày sinh, ngày nhập viện) thì lưu dạng '2026-03-15' plain date, không để thành Date — nếu không, chuyển timezone sẽ làm ngày sinh nhảy 1 hôm. Đây là bug em từng gặp thật.
  5. Intl.DateTimeFormat nên khởi tạo một lần ở module scope, không tạo trong render — nó khá nặng.

Không tìm thấy câu hỏi nào khớp từ khoá.
