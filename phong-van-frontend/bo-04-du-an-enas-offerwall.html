Form engine & schema

3 câu
Q1 Form builder của bạn sinh form từ schema. Khi khách đã publish form và thu được 10.000 lead, rồi họ sửa schema — dữ liệu cũ xử lý thế nào? ▸
Gợi ý trả lời

Đây là câu hỏi hay nhất về form builder và là chỗ thiết kế non tay sẽ vỡ. Cốt lõi: schema phải có version, và submission phải trỏ tới version nó được tạo bằng.

form            { id, name, currentVersionId }
form_version    { id, formId, version, schema (JSON), publishedAt }
submission      { id, formId, formVersionId, data (JSON), createdAt }

Ba loại thay đổi và cách xử:

Thay đổiẢnh hưởng dữ liệu cũCách làm
Thêm field mớiKhông phá gìBản ghi cũ hiện "—" ở cột mới. Tạo version mới, an toàn.
Đổi label, đổi thứ tựKhông pháVersion mới. Khi xem lead cũ thì render theo schema version của nó, nên vẫn đúng ngữ cảnh lúc thu.
Xoá field / đổi type (text → number)PháKhông xoá dữ liệu. Field bị ẩn khỏi form mới nhưng vẫn giữ trong submission cũ; khi export thì cột đó chỉ có giá trị ở các lead cũ. Đổi type thì em cảnh báo rõ trên UI và tạo field mới thay vì đổi tại chỗ.

Nguyên tắc em áp dụng:

  1. Không bao giờ sửa schema đã publish tại chỗ — luôn tạo version mới. Giống migration DB: không sửa file migration cũ.
  2. Dùng fieldKey bất biến, không dùng label làm khoá. Khách đổi label từ "Họ tên" sang "Tên đầy đủ" thì dữ liệu vẫn phải nối đúng. Đây là lỗi kinh điển: dùng label làm key thì đổi label là mất toàn bộ dữ liệu cũ.
  3. Xem lại lead cũ thì render bằng schema version của nó, không phải version hiện tại. Nếu render bằng version mới thì dữ liệu cũ hiển thị sai chỗ hoặc mất.
  4. Export CSV là union các field của mọi version trong khoảng thời gian được chọn, ô nào không tồn tại ở version đó thì để trống — chứ không phải để 0 hay "null".
  5. Cảnh báo trên UI trước khi publish: "Thay đổi này xoá 1 câu hỏi. 10.000 lead đã thu vẫn được giữ nhưng form mới sẽ không hỏi mục này nữa." Người dùng phải hiểu hậu quả trước khi bấm.
⭐

Điểm ăn tiền: Nếu dự án thật của bạn chưa làm versioning, hãy nói thật: "dự án lúc đó chỉ lưu một schema, và em đã gặp đúng vấn đề này khi khách đổi field — nếu làm lại em sẽ version từ đầu". Nhận ra vấn đề vẫn ăn điểm; giả vờ đã làm rồi bị đào là mất điểm.

Q2 Kể về kiến trúc 4 layer của form engine. Vì sao không viết một component to rồi switch-case? ▸
Gợi ý trả lời

Bốn layer:

schema     JSON mô tả field: { key, type, label, rules, visibleWhen }
             -> nguồn sự thật duy nhất, lưu DB, dùng cho cả builder và form public
converter  schema <-> API shape; sinh validation schema (Zod) từ rules
             -> BE đổi shape thì chỉ sửa ở đây
layout     grid, thứ tự, group, responsive, logic hiện/ẩn theo điều kiện
             -> không biết gì về UI component cụ thể
ui         registry: { text: TextInput, select: SelectInput, postal: PostalInput, ... }
             -> thêm loại field = thêm 1 entry, KHÔNG sửa core
// registry — trái tim của kiến trúc
const FIELD_REGISTRY = {
  text:   { Component: TextInput,   toZod: (r) => applyString(z.string(), r) },
  number: { Component: NumberInput, toZod: (r) => applyNumber(z.number(), r) },
  select: { Component: SelectInput, toZod: (r) => z.string().min(r.required ? 1 : 0) },
  postal: { Component: PostalInput, toZod: () => z.string().regex(/^\d{3}-?\d{4}$/) },
};

function FieldRenderer({ field, ...props }) {
  const entry = FIELD_REGISTRY[field.type];
  if (!entry) return <UnknownField type={field.type} />;   // fail mềm, không crash cả form
  return <entry.Component field={field} {...props} />;
}

Vì sao không switch-case một component to:

  • Với switch-case, thêm field type là sửa file core → mỗi lần sửa là rủi ro làm vỡ field khác, và 2 người thêm 2 field cùng lúc là conflict. Registry thì mỗi field một file, không ai đụng ai.
  • Đây đúng là Open/Closed Principle: mở để mở rộng, đóng để sửa đổi.
  • Validation sinh từ schema, không viết tay 2 lần. Rule "required" khai báo một lần trong schema, converter biến thành Zod cho runtime và cùng lúc là nguồn type qua z.infer.
  • EFO features làm một lần ở layer layout — auto-focus field kế tiếp, validate realtime, thanh tiến độ, nhớ giá trị đã nhập — áp dụng cho mọi form của mọi khách, không phải code lại từng form.

Kết quả đo được: khi PO yêu cầu thêm field postal-code auto-fill địa chỉ (rất phổ biến ở Nhật — gõ mã bưu chính là tự điền tỉnh/thành), em thêm 1 component + 1 entry registry, không sửa engine. Từ yêu cầu tới release mất dưới một ngày.

Q3 A/B testing cho form variant — bạn implement phía FE thế nào? Làm sao đảm bảo cùng một người luôn thấy cùng variant? ▸
Gợi ý trả lời

Nguyên tắc: việc chia variant phải deterministic và phải ổn định theo người dùng.

  1. Gán variant bằng hash, không bằng random. variant = variants[hash(visitorId + experimentId) % variants.length]. Random thì user reload là thấy form khác — dữ liệu thí nghiệm vô nghĩa và UX tệ.
  2. visitorId sinh một lần lưu cookie first-party (không phải localStorage, vì form được nhúng iframe vào site khách nên cần cookie để bền hơn). Nếu user đã đăng nhập thì dùng userId để nhất quán qua nhiều thiết bị.
  3. Quyết định ở đâu: lý tưởng là server (hoặc edge) quyết định và trả về HTML/config đã chọn variant. Nếu để client quyết thì có flash — user thấy variant A nhoáng rồi đổi sang B, vừa xấu vừa làm nhiễu số liệu. Với ENAS là Next.js App Router nên em đọc cookie ở Server Component và render đúng variant ngay từ HTML đầu tiên.
  4. Tracking: phải log cả impression (đã thấy variant nào) và conversion (submit thành công), gắn cùng visitorId + variantId. Chỉ log conversion thì không tính được tỉ lệ.

Ba cái bẫy em phải nói ra:

  • Đổi variant giữa thí nghiệm làm nhiễu dữ liệu — phải "đóng băng" cấu hình khi experiment đang chạy, muốn sửa thì tạo experiment mới.
  • Sample size: khách hay dừng thí nghiệm sau 50 lượt và tuyên bố variant B thắng. UI nên hiện rõ "chưa đủ dữ liệu để kết luận" — em đưa cảnh báo dựa trên ngưỡng tối thiểu, dù phần thống kê chuẩn (significance) do BE tính.
  • Nhiều experiment cùng lúc trên cùng form sẽ chồng chéo. Em giới hạn một form chỉ chạy một experiment tại một thời điểm — đơn giản hoá bằng ràng buộc nghiệp vụ, thay vì làm hệ thống multi-variate phức tạp mà khách không dùng.

Q4 Template Builder của Offerwall: 9 loại block, kéo thả, preview trong khung điện thoại. Làm sao đảm bảo preview giống hệt bản thật? ▸
Gợi ý trả lời

Quy tắc số một: preview và bản public phải dùng CHUNG một bộ renderer. Viết hai bản là chắc chắn lệch sau vài sprint — khách thấy preview đẹp, wall thật khác, và đó là loại bug mất niềm tin nhất.

// dùng chung
<WallRenderer config={config} />

// preview chỉ khác ở wrapper
<PhoneFrame width={375}>
  <PreviewContext.Provider value={{ interactive: false, scale }}>
    <WallRenderer config={draftConfig} />
  </PreviewContext.Provider>
</PhoneFrame>

Bốn vấn đề thực tế và cách giải:

  1. Responsive trong khung hẹp. Preview rộng 375px nhưng nằm trong trang desktop, nên @media (max-width: …) không kích hoạt — media query tính theo viewport, không theo container. Giải: dùng container query, hoặc truyền breakpoint qua context thay vì media query. Đây là bẫy rất hay gặp.
  2. Tương tác trong preview. Bấm vào block trong preview phải là "chọn block để sửa", không phải "mở link offer". Giải: interactive: false qua context, renderer tự chặn navigation; và một lớp overlay bắt click để chọn block.
  3. Đồng bộ hai chiều. Chọn block ở panel trái phải scroll preview tới đó và highlight; ngược lại click preview phải chọn đúng item ở panel. Giải: mỗi block có id ổn định, dùng scrollIntoView + state selectedId dùng chung.
  4. Font và ảnh. Wall thật load từ CDN của khách; preview trong admin phải load cùng nguồn, không thì màu/font lệch. Em phải xử cả CORS cho font.
Q5 Kéo thả 9 block mà không lag. Bạn tối ưu thế nào? Undo/redo làm sao? ▸
Gợi ý trả lời

Tối ưu kéo thả — nguyên tắc: trong lúc drag thì không đụng vào store global.

  1. State kéo thả là cục bộ: vị trí tạm giữ trong ref/local state của layer drag, chỉ commit vào store khi drop. Nếu mỗi onDragOver đều dispatch thì cả cây re-render 60 lần/giây.
  2. Memo từng block + props ổn định (useCallback cho handler). Không thì kéo 1 block là render cả 9.
  3. Chỉ animate transform, không animate top/left hay margin — transform chạy trên compositor, không trigger layout/paint.
  4. Preview debounce nhẹ (~100ms) trong lúc kéo: cấu hình đổi liên tục nhưng preview không cần cập nhật từng frame.
  5. Em dùng react-beautiful-dnd / react-grid-dnd; nếu làm lại giờ em sẽ chọn dnd-kit — nhẹ hơn, hỗ trợ touch tốt hơn và không bị deprecated.

Undo/redo: em làm bằng history stack các snapshot, không phải command pattern:

// Zustand store
{
  present: config,
  past:    [],      // snapshot trước đó
  future:  [],      // để redo

  commit(next) {
    set(s => ({
      past:    [...s.past.slice(-49), s.present],   // giới hạn 50 bước
      present: next,
      future:  [],                                  // hành động mới xoá nhánh redo
    }));
  },
  undo() { /* dịch present sang future, lấy từ past */ },
}

Lý do chọn snapshot thay vì command: config của một wall chỉ vài chục KB JSON, giữ 50 snapshot là không đáng kể, mà code đơn giản hơn nhiều lần — command pattern cần viết cặp do/undo cho mỗi loại hành động và rất dễ sai. Nếu tài liệu lớn (kiểu Figma) thì mới cần command/patch (immer produceWithPatches cho patch nhỏ).

Chi tiết dễ quên: gộp các thay đổi liên tiếp cùng loại thành một bước undo — gõ 10 ký tự vào label không nên là 10 lần undo. Em debounce commit cho input text (~500ms) nhưng commit ngay cho hành động rời rạc (thêm/xoá/đổi thứ tự block).

Q6 Offerwall build static export deploy S3/CloudFront. Refresh trang con thì bị 404 — vì sao và sửa thế nào? ▸
Gợi ý trả lời

Nguyên nhân: SPA route /wall/123/detail chỉ tồn tại trong JS router, không phải file thật trên S3. Vào trang chủ rồi điều hướng nội bộ thì ổn (router xử lý), nhưng gõ URL trực tiếp hoặc F5 thì browser gửi request thật lên S3 → không có object /wall/123/detail → 404.

Cách sửa:

  1. CloudFront custom error response: map 403/404 → trả /index.html với status 200. Đây là cách em dùng. Lưu ý phải là 200, không phải 404 — nếu trả 404 thì SEO và một số client sẽ hiểu sai.
  2. Hoặc S3 static website hosting với error document = index.html (nhưng mất khả năng dùng OAC/private bucket).
  3. Hoặc CloudFront Function rewrite request không có extension về /index.html — linh hoạt nhất, xử lý được cả trailing slash.

Ba vấn đề đi kèm của static export mà em gặp:

  • Cache invalidation. index.html phải Cache-Control: no-cache (luôn hỏi lại server), còn asset có hash trong tên (main.a3f9.js) thì max-age=31536000, immutable. Nếu cache index.html lâu thì deploy xong user vẫn thấy bản cũ hàng giờ. Đây là lỗi em từng gặp và mất cả buổi để hiểu.
  • Chunk cũ biến mất sau deploy. User đang mở tab, ta deploy bản mới xoá chunk cũ, user điều hướng sang route lazy-load → lỗi "Failed to fetch dynamically imported module". Giải: giữ file build cũ trên S3 vài phiên bản (không xoá ngay), và bắt lỗi import động để hiện "Có bản cập nhật mới, tải lại trang?" rồi location.reload().
  • Env variable bị inline lúc build. Next/Vite nhúng NEXT_PUBLIC_*/VITE_* vào bundle, nên một build không dùng được cho nhiều môi trường. Hoặc build riêng mỗi env, hoặc tải config runtime từ một file config.json không cache — em chọn cách hai khi cần một artifact dùng cho cả staging và production.
⭐

Điểm ăn tiền: Câu này chứng minh bạn đã vận hành chứ không chỉ code. Ba vấn đề cache/chunk/env là thứ chỉ người deploy thật mới biết.

Q7 Stripe thanh toán khi submit form. Làm sao không bị tính tiền 2 lần? ▸
Gợi ý trả lời

Nguyên tắc nền: FE không bao giờ là nơi quyết định "đã thanh toán thành công". Sự thật nằm ở webhook từ Stripe về BE.

Luồng em làm:

  1. FE gọi BE tạo PaymentIntent, BE trả clientSecret. Số tiền do BE quyết định, không nhận từ FE — nếu nhận từ FE thì user sửa request là trả 1đ.
  2. FE dùng Stripe.js (confirmPayment) — thông tin thẻ không đi qua server của mình (giảm phạm vi PCI-DSS).
  3. Stripe gọi webhook về BE → BE verify signature → mới ghi "đã thanh toán" và tạo submission.
  4. FE chỉ hiển thị trạng thái, và poll hoặc chờ redirect để biết kết quả — không tự kết luận từ response của confirmPayment.

Chống trùng (đây là phần họ muốn nghe):

  • Idempotency key khi tạo PaymentIntent: FE sinh một key cho mỗi lần user bắt đầu thanh toán, gửi kèm. User bấm nút 3 lần hoặc mạng timeout rồi retry → Stripe trả lại cùng intent, không tạo mới.
  • Disable nút ngay khi bấm + hiện loading. Đơn giản nhưng chặn được phần lớn double-submit.
  • Webhook phải idempotent ở BE: Stripe có thể gửi lại cùng event nhiều lần (at-least-once delivery). BE lưu event.id đã xử lý và bỏ qua trùng.
  • Không tin redirect: user có thể đóng tab trước khi redirect về. Webhook mới là nguồn sự thật, nên đơn hàng vẫn hoàn tất đúng.

Xử lý 3D Secure (bắt buộc ở Nhật/EU): confirmPayment có thể trả về trạng thái cần xác thực thêm → Stripe mở modal/redirect. FE phải xử lý được cả trường hợp quay lại trang từ redirect với payment_intent_client_secret trong URL, và hiện đúng trạng thái đang chờ.

Q8 i18n JP/EN — cái gì khó ngoài việc dịch chuỗi? ▸
Gợi ý trả lời

Dịch chuỗi là phần dễ nhất. Những cái thật sự khó:

  1. Độ dài text. Tiếng Nhật ngắn hơn khi đếm ký tự nhưng rộng hơn khi render (ký tự full-width), còn tiếng Đức/Anh thì dài hơn nhiều. Nút thiết kế vừa khít tiếng Nhật sẽ vỡ ở tiếng Anh. Giải: không fix width cho nút/label, luôn test cả 2 locale, và ưu tiên layout tự giãn.
  2. Xuống dòng tiếng Nhật. Tiếng Nhật không có space giữa từ, browser có thể cắt dòng ở chỗ vô nghĩa. Dùng word-break: normal + line-break: strict, và với tiêu đề quan trọng thì dùng <wbr> hoặc ký tự zero-width để kiểm soát điểm cắt.
  3. Plural và interpolation. Tiếng Nhật không phân biệt số ít/nhiều, tiếng Anh thì có. Không được nối chuỗi thủ công (count + ' items') — phải dùng t('items', { count }) và để i18next chọn dạng đúng theo locale.
  4. Thứ tự tên người. Nhật là họ trước tên sau, và có cả furigana (cách đọc) như một field riêng — form đăng ký ở Nhật thường có 4 field: 姓/名 (kanji) + セイ/メイ (katakana). Không thể dùng chung component "Full name".
  5. Địa chỉ. Nhật đi từ lớn đến nhỏ (tỉnh → thành phố → khu → số), ngược với Anh/Mỹ. Và postal code auto-fill là kỳ vọng mặc định: gõ 7 số là phải tự điền tỉnh/thành. Không có tính năng này là khách Nhật thấy form "chưa xong".
  6. Ngày và năm. Ngoài YYYY/MM/DD, một số văn bản hành chính Nhật dùng niên hiệu (令和 6年 = 2024). Nếu nghiệp vụ cần thì phải dùng Intl.DateTimeFormat('ja-JP-u-ca-japanese').
  7. Chuỗi trong code. Cấm hard-code — em thêm lint rule chặn literal text trong JSX. Và không nối chuỗi từ nhiều key (t('you have') + n + t('messages')) vì ngữ pháp mỗi ngôn ngữ khác nhau; luôn dùng một key có placeholder.

Về kỹ thuật với Next.js: dùng next-i18next (Pages Router) / next-intl (App Router), tách namespace theo module để không tải hết file dịch của cả app trong một trang, và chỉ tải locale đang dùng.

Q9 Webhook và tích hợp Salesforce — phần FE làm gì? Bạn thiết kế UI cho việc này thế nào? ▸
Gợi ý trả lời

Webhook là chuyện của BE, nhưng UI quản lý webhook là một bài toán UX thật sự — và là chỗ dễ làm dở.

Những gì FE phải có:

  1. Tạo/sửa endpoint + chọn event nào gửi + hiện signing secret (chỉ hiện đầy đủ một lần lúc tạo, sau đó mask — và nói rõ điều đó trên UI).
  2. Nút "Gửi thử": cực kỳ quan trọng. Khách cấu hình webhook xong không biết nó có chạy không. Nút test gửi payload mẫu và hiện ngay response (status, body, thời gian) → khách tự debug được, giảm ticket support rất nhiều.
  3. Delivery log: bảng lịch sử gửi — thời điểm, event, status code, số lần retry, payload và response (thu gọn được). Kèm nút gửi lại cho lần thất bại.
  4. Trạng thái sức khoẻ: nếu endpoint fail liên tục thì hiện badge cảnh báo ở danh sách, không để khách tự phát hiện sau 3 ngày mất dữ liệu.
  5. Salesforce: luồng OAuth — FE mở popup/redirect tới Salesforce, nhận callback, rồi UI mapping field: field form của mình ↔ field object Salesforce. Phần mapping này là cái khó nhất: phải fetch được danh sách field từ Salesforce (BE proxy), cảnh báo field required của Salesforce chưa được map, và validate type tương thích.

Hai điều em học được:

  • Không bao giờ hiện secret/token đầy đủ sau lần đầu, và không log nó ra console hay Sentry. Em đã phải thêm scrub rule vì stack trace có lúc chứa header Authorization.
  • Trạng thái "đang kết nối" phải rõ ràng. OAuth có thể hết hạn refresh token — UI phải phân biệt được "chưa kết nối", "đã kết nối", "kết nối hết hạn cần cấp phép lại". Gộp 3 trạng thái này thành boolean là khách sẽ mất dữ liệu mà không biết.
Q10 Dashboard 7 tab báo cáo + export CSV. Có gì đáng nói về kỹ thuật? ▸
Gợi ý trả lời

Nhìn thì nhàm nhưng có 5 điểm kỹ thuật thật:

  1. Tab là URL, không phải state. /analytics?tab=revenue&from=…&to=… — để khách bookmark và gửi link cho đồng nghiệp thấy đúng báo cáo. Đây là yêu cầu nghiệp vụ mà dev hay bỏ qua.
  2. Không fetch cả 7 tab cùng lúc. Lazy theo tab đang mở, nhưng prefetch tab kế bên khi hover. Với React Query là queryClient.prefetchQuery — cảm giác mượt mà không tốn 7 request ngay từ đầu.
  3. Filter dùng chung nhiều tab thì đưa vào queryKey của từng query: ['analytics', tab, from, to, filters]. Đổi khoảng ngày thì mọi tab tự invalidate đúng, không phải tự quản lý.
  4. Export CSV — đây là chỗ hay làm sai. Không export từ dữ liệu đang hiện trên màn hình (đó chỉ là 1 trang phân trang). Đúng là gọi endpoint export riêng ở BE, để BE stream file. Với dữ liệu lớn thì làm async: tạo job → BE gửi email hoặc FE poll rồi hiện link tải. Cố export 500.000 dòng trong một request HTTP là timeout.
  5. CSV cho Excel tiếng Nhật: phải có BOM UTF-8 ở đầu file, không thì Excel trên Windows mở ra là ký tự lỗi — khách Nhật báo bug ngay. Và dấu phân cách nên theo locale (một số cấu hình Excel JP dùng ;). Đây là chi tiết rất nhỏ nhưng em bị report thật.

Về chart (ApexCharts ở Bidding Assistant, tương tự ở đây): chart lib nặng nên phải lazy-load, chỉ import module cần dùng, và nhớ rằng nhiều chart lib không SSR được — phải dynamic(..., { ssr: false }) trong Next.
